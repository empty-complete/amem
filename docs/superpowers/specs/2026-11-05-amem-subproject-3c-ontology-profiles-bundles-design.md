# amem — подпроект 3c: онтология домена, профили сущностей и обмен подборками

Редакция 1 (05.11.2026).

Продолжение спецификаций ядра (`2026-10-25-amem-core-split-design.md`, разд. 4 «Пакеты домена») и автопроверки (`2026-11-05-amem-subproject-3-autocheck-design.md`). Номер 3c — потому что это библиотечная работа до сервера (подпроект 4): сервер и интерфейс лишь показывают то, что описано здесь. С автопроверкой подпроект связан движком шаблонов: профиль сущности — это шаблон, и проверяет его тот же код.

## Зачем

amem задуман как личная база одного человека, в которой живут несколько областей сразу: рабочие объекты, научная работа, учебный проект с коллегой. У областей разные виды знаний, но они пересекаются: формулы и величины нужны и в науке, и в расчётах; решения и уроки — везде. Три потребности, которых нынешнее ядро не закрывает:

1. **Объект домена и его параметры.** У вещи, с которой работают (здание, конструкция, устройство, образец), есть набор параметров, который нужно собрать, прежде чем с ней что-то делать — рассчитать, заказать, опубликовать. Набор задаётся областью, расширяется, у него есть обязательные поля, умолчания и источники. Сегодня amem хранит параметры атомами `parameter` о сущности, но не знает, *какие* параметры у сущности этого класса должны быть, и не умеет сказать, чего не хватает.
2. **Человек пишет сам.** Заметки, решения и наблюдения человек записывает без файла-источника и правит человекочитаемый текст атомов. Сегодня интерфейс `has_source` отклоняет атом без источника, а статусы рассчитаны на предложения модели.
3. **Подборки переносятся между базами.** Ветку знаний — по проекту, тегу или набору объектов — один человек отдаёт другому вместе с онтологией, которой она пользуется; получатель вливает её в свою базу, ничего не теряя и не затирая. Задел (`base_id`, `provenance.origin_base`) есть, самого обмена нет.

| Потребность | Есть | Не хватает |

| Записи человека | `agent` вида `person:`; политика «правка проверенной записи ждёт человека» | политика статусов для записей самого человека; шаблоны, которые действуют только на предложения модели |
| Уверенность распознавания | `confidence` у связи | `confidence` у атома, правило риска по низкой уверенности |
| Место в файле | селекторы `page`, `sheet`, `range`… | селектор координат на странице (`bbox`) — для распознанных чертежей |
| Обмен | `base_id` в `meta`, `provenance.origin_base`, `backup.create/snapshot` (вся база целиком) | формат подборки, отбор по проекту, тегу и объектам, импорт без потерь и без молчаливой перезаписи, перенос пакетов |

## Решения

| Вопрос | Решение |
|---|---|
| Где живёт онтология области | В пакете домена. Ядро — общее для всех; область — пакет; общее для нескольких областей — отдельный пакет, который они требуют (`requires`). У проекта своей онтологии нет: проект — сущность `project`, он *пользуется* пакетами |
| Пересечение областей | Код принадлежит одному пакету. Две области делят код только через общий пакет-зависимость, не копированием |
| «Какие параметры нужны объекту» | Раздел `parameters` у шаблона сущности (`target: entity`) — профиль. Наследование профилей — тем же `extends` |
| Параметр объекта в базе | Атом `parameter` о сущности с `content.values[0].property` — как сейчас; новых таблиц содержания нет. Проекция `atom_property` ускоряет отбор |
| Карточка объекта | Не хранится — вычисляется из атомов: `profile.card(entity)` даёт поля профиля с состоянием `known` / `missing` / `asked` / `na` / `conflict` и собирает цепочку `part_of`. Формат `amem.card/1`; внешние расчётные форматы — забота их владельцев |
| Значение без документа | Поле атома `basis`: `default` (умолчание методики), `assumed` (допущение), `author` (утверждение автора). При заданном `basis` источник не обязателен; `author` может ставить только агент `person:` |
| Записи человека | Новая запись агента `person:` получает `verified`, в очередь не ставится, риск шаблонов к ней не применяется; уровни 1–2 выполняются как для всех. Правка записи человека моделью — `pending`, как сейчас |
| Уверенность | `confidence` (0…1) у атома; правило риска `low_confidence` (порог 0,8) для шаблонов |
| Подборка | Папка (или zip) формата `amem.bundle/1`: манифест, записи JSONL, связи, объекты, по желанию файлы и пакеты. Отбор — по тегам, проекту, видам, классам, явным ссылкам; замыкание — сущности `about`, редакции, связи внутри подборки |
| Импорт | Id сохраняются. Нет записи — создаётся с тем же id; есть и совпадает — пропуск; есть и отличается — новая ревизия `pending` с причиной `imported`. Ничего не затирается. Пакеты должны быть загружены с тем же digest — иначе отказ до записи |
| Доверие при импорте | `trust=keep` (по умолчанию): статусы остаются, происхождение видно в `provenance`; `trust=review`: всё импортированное — `needs_review` с пунктом `imported` |
| Совместимость | Схема записей остаётся `amem.atom/1` и `amem.entity/1`: новые поля необязательны. Ядро — 1.2.0 |

## 1. Онтология: слои и пакеты

### 1.1. Три слоя

```
ядро core          виды, классы, связи, селекторы, интерфейсы — общее для любой области
общие пакеты       то, что делят несколько областей: величины и единицы, формулы, обозначения
доменные пакеты    область: свои классы сущностей, величины, профили, шаблоны, навыки
```

Проект (сущность `project`) не задаёт словаря. Атомы проекта помечены `scope.project`, его объекты связаны `about` и `part_of`; какие пакеты проект использует, выводится из кодов его записей (разд. 4.2). Личные заметки идут видом ядра `note` — без пакета.

### 1.2. Зависимости пакетов

`pack.yaml` получает необязательный раздел:

```yaml
name: facade
version: 1.0.0
requires:
  quantities: ">=1.0.0,<2"
```

Правила загрузки (`packs.load_packs`, до записи в базу):
- каждый требуемый пакет присутствует среди загружаемых, его версия входит в диапазон (semver: `>=`, `<`, `==`, через запятую);
- порядок загрузки — топологический: зависимость раньше зависимого; цикл — ошибка с цепочкой имён;
- `core` требовать не нужно — он всегда первый; явное `requires: {core: …}` допустимо и проверяется так же;
- ошибки называют пакет, файл и чего не хватает: «пакет facade требует quantities >=1.0.0,<2, загружен 0.9.1».

Таблица `pack` получает столбец `requires jsonb` (как записано в манифесте) — чтобы подборка (разд. 4) и будущий интерфейс могли показать дерево пакетов без чтения папок.

### 1.3. Ядро 1.2.0

Добавляется:

| Схема | Код | Смысл |
|---|---|---|
| `kind` | `note` | Заметка человека: наблюдение, мысль, напоминание. Источник — сам автор (`basis: author`) |
| `entity_class` | `artifact` | Вещь, сделанная людьми: изделие, устройство, конструкция, узел, образец. Доменные классы уточняют его через `broader: artifact` |
| `selector_type` | `bbox` | Прямоугольник на странице: `x0,y0,x1,y1` в пунктах PDF от левого верхнего угла; уточняет `page` или `sheet` через `refined_by` |
| `property` | — | Пусто, как раньше: величины приходят из пакетов и от агентов |

Шаблоны ядра:
- `has_source` 1.1.0: оба правила (`sources` и `sources[].selectors`) получают `skip_if_set: basis` (разд. 2.3);
- новый шаблон `note` (`applies_to: note`, `extends: [has_label]`): `body` обязателен (`warning`), связи — любые;
- `has_label`, `has_value`, `decision` — без изменений.

`Concept.broader` уже есть в схеме; загрузчик начинает его проверять: код `broader` существует в той же схеме среди загружаемых пакетов.

## 2. Схема записей: основание, уверенность

### 2.1. `basis` у атома

```yaml
Basis:
  default:  умолчание методики — значение не взято из документа об объекте, а принято по правилу области «в запас»
  assumed:  допущение — принято без решения по объекту, чтобы продолжить работу; требует подтверждения
  author:   утверждение автора — человек говорит это сам, документа нет
```

`AtomPayload.basis` — необязательное поле. Правила уровня 1:
- `basis: author` у записи агента `model:` — `violation` `basis_author_model`;
- `basis: default` или `assumed` без `derived_from` — `warning` `basis_without_rule`: откуда правило, по которому принято умолчание, должно быть видно; целью `derived_from` обычно служит атом `method` или `decision` пакета;
- вид атома `basis` не ограничивает: умолчание бывает у параметра, утверждение автора — у заметки, решения, факта или вопроса.

### 2.2. `confidence` у атома

`AtomPayload.confidence` — число от 0 до 1, уверенность агента-модели в утверждении (распознавание чертежа, извлечение из скана). Человек поле не заполняет: у записи `person:` поле `confidence` — `violation` `confidence_person`. Новое правило риска `HighRiskRule.low_confidence`: записи с `confidence < 0.8` уходят к человеку (`needs_review`, пункт `high_risk`). Порог — константа `check.LOW_CONFIDENCE`; шаблон включает правило строкой `high_risk: [low_confidence]`. Без правила в шаблоне низкая уверенность ничего не меняет — она только хранится и видна в выдаче.

### 2.3. `skip_if_set` у правила поля

`FieldRule.skip_if_set` — путь до поля того же тела; если оно непусто, правило не применяется. Нужно `has_source`: источник не обязателен, когда задано основание. Проверка пути — тем же `_check_path`. Одно такое поле на правило; сложнее условий шаблонам не дают — остальное решает уровень 5.

## 3. Профиль сущности и карточка

### 3.1. Профиль — раздел шаблона

Шаблон с `target: entity` получает раздел `parameters`:

```yaml
code: glazing
version: 1.0.0
target: entity
applies_to: glazing
extends: [artifact_profile]
parameters:
  - property: height            # код словаря property загружаемых пакетов
    required: true              # без него с объектом работать нельзя (блокер)
    group: geometry             # свободный код группы — для порядка в карточке
    origin: recognized          # код словаря parameter_origin (разд. 3.2), необязателен
    default: {amount: 0, unit: deg}   # умолчание: amount+unit или value_text; необязательно
    ask: {ru: "проектировщик"}  # кому задавать вопрос, если значения нет
    hint: {ru: "разрезы, фасады"}      # где искать
    when: {ru: "только для наклонных конструкций"}  # условие применимости; поле может быть na
```

`ParameterRule`: `property` (обязательно), `required` (по умолчанию `false`), `group`, `origin`, `default` (`amount`, `unit`, `value_text`), `ask`, `hint`, `when` (все — `LangString`). Порядок правил в карточке — порядок в файле, у наследника — правила предков, затем свои.

Сведение по наследованию — как у `fields`, но по ключу `property`: правило потомка заменяет правило предка с той же величиной. Шаблон-интерфейс (без `applies_to`) с `parameters` действует на все сущности своего `target` — так общий пакет может потребовать, например, `label`-величину у всех изделий; на практике профили — у конкретных классов.

Проверка при загрузке пакетов (`packs._check_template`):
- `property` каждого правила есть в схеме `property` загружаемых пакетов;
- `origin` есть в схеме `parameter_origin`;
- `default.unit` — код UCUM; если у величины задана единица, `default.unit` в неё переводится;
- `property` не повторяется в одном шаблоне;
- у шаблона с `target: atom` или `link` раздела `parameters` нет — ошибка.

### 3.2. Словарь `parameter_origin`

Открытая схема понятий: откуда область берёт значение и чья задача, если его нет. Ядро её не заполняет. Пример доменного пакета:

```yaml
scheme: parameter_origin
concepts:
  - {code: recognized, label: {ru: распознаётся из документации}, definition: {ru: "Парсер ищет, человек проверяет."}}
  - {code: other_section, label: {ru: другой раздел проекта}, definition: {ru: "Запросить раздел."}}
  - {code: external, label: {ru: внешний запрос}, definition: {ru: "Заказчик или поставщик."}}
  - {code: method, label: {ru: решение по методике}, definition: {ru: "Умолчание в запас, подтверждает конструктор."}}
  - {code: reference, label: {ru: справочная база}, definition: {ru: "Климат, материалы, редакции норм."}}
```

### 3.3. Параметры в базе и проекция `atom_property`

Параметр объекта — атом `kind: parameter`, `about: [ent:…]`, `content.values[0].property` — код величины. Один атом — одна величина об одной сущности; несколько сущностей в `about` допустимы (значение общее для них).

Новая таблица-проекция `atom_property (revision_id, property)` — ключ по ревизии, как у `atom_about`, — заполняется при записи ревизии в `records._refresh` вместе с `atom_about`, из всех `content.values[].property` текущей ревизии. Индекс по `(property, revision_id)`. Проекция производная, как `search_document`: триггеров неизменяемости у неё нет, `rebuild_projections` может её стереть и построить заново. Внешнего ключа на `concept` нет: коды величин свободны (неизвестный — предупреждение `unknown_property`). Это даёт отбор «атомы с величиной X о сущности Y» одним соединением `atom_about ⋈ atom_property` без разбора JSONB. Новая функция `records.rebuild_projections(conn)` идемпотентно перестраивает `atom_about`, `atom_derived` и `atom_property` из текущих ревизий; тест сверяет результат с построчным разбором.

### 3.4. Карточка

```python
profile.card(conn, ref, *, ancestors=True) -> dict   # формат amem.card/1
```

Для сущности берётся сведённый профиль её класса (активные шаблоны). Для каждого правила ищутся действующие атомы `parameter` с этой величиной о сущности: текущая ревизия, статус не `rejected`, `deprecated`, `superseded`. Состояние поля:

| Состояние | Условие |
|---|---|
| `missing` | атомов нет; или единственное значение — `value_state: unknown` (документ величину не называет) |
| `asked` | атомов `parameter` нет, но есть действующий атом `question` о сущности с этой величиной (`content.values[].property`, `value_state: unknown`) |
| `na` | значение `value_state: none` — величина к объекту не относится |
| `conflict` | два и более действующих значения, различных после перевода единиц, и ни одно не `rank: preferred` |
| `known` | одно значение; или среди нескольких одно `preferred` (остальные — в `candidates`) |

Пограничные случаи: `none` + `unknown` → `na`; `none` + известное значение → `conflict`; `unknown` + вопрос → `asked`; вопросом считается только атом `question` с `value_state: unknown` у этой величины. Значения сравниваются после перевода к единице величины из словаря, а если её там нет — к единице первого значения поля, с относительной точностью 1e-9. Значения с `rank: deprecated` учитываются, только если других нет, и в `candidates` не попадают. Из нескольких атомов с одним значением признаки поля (`by`, `status`, `basis`, источники) берутся у лучшего: сначала `verified`, затем автор `person:`, затем более новая ревизия. `profile` — шаблон, давший правила профиля (последний по порядку применения); `null` — только если правил профиля нет.

У поля `known` вместе со значением отдаются признаки, из которых потребитель собирает свой рабочий статус: `basis` (`null`, `default`, `assumed`, `author`), `by` (`person` / `model` — агент текущей ревизии), `status` атома, `source_role` (`primary` / `secondary` / `derived`), `confidence`, источники со вердиктами сверки, ссылки `atm:`. Расчётное ядро, которому нужно «распознано / подтверждено / вычислено / умолчание», получает всё для этого: `by = model` без `verified` — распознано; `verified` или `by = person` — подтверждено; `source_role = derived` — вычислено; `basis = default` — умолчание.

Сводка карточки: число полей по состояниям, число открытых блокеров (`required` и состояние не `known` и не `na`), список полей с `basis`. Умолчание из профиля в карточке показывается рядом с полем, но **значением не считается**: пока атома нет, поле `missing`. Принять умолчание — значит записать атом с `basis: default` и `derived_from` на правило; это действие человека или агента, не карточки.

`ancestors=True`: по связям `part_of` (действующим, сущность→сущность) вверх собираются карточки предков — конструкция → здание → площадка; у каждой свой профиль по своему классу. Цикл `part_of` обрывается по посещённым; глубина не ограничена. Карточка потомка на предка не ссылается значениями: кто какой величиной пользуется, решает потребитель.

Сущность без профиля (у класса нет шаблона с `parameters`) даёт карточку с пустым `fields` и всеми действующими атомами `parameter` в `extra` — так видно, что о ней известно, даже если область ещё не описала класс. Величины, которых в профиле нет, но атомы есть, тоже попадают в `extra`.

### 3.5. Что карточкой не делается

- Вывод значения из значений предка (высота здания для конструкции) — потребитель.
- Запись умолчаний «одним нажатием» — действие интерфейса (подпроект 5) через обычный `submit`.
- Внешние форматы расчётных карточек — конвертер в репозитории того расчёта; `amem.card/1` даёт ему всё необходимое.

## 4. Подборки: экспорт и импорт

### 4.1. Отбор

```python
bundle.Selection(tags=(), project=None, kinds=(), entity_classes=(), refs=(), statuses=DEFAULT, since=None)
```

Запись попадает в подборку, если подходит под **все** заданные условия (пустое условие не ограничивает): есть хоть один из тегов; `scope.project` или `about` ведёт на проект (для сущностей — есть атом подборки о ней либо она достижима по `part_of` от сущности подборки); вид или класс из перечня; явная ссылка `atm:` / `ent:`; статус из перечня (по умолчанию — все, кроме `rejected`); `recorded_at` текущей ревизии не раньше `since`.

Замыкание — всегда:
- сущности из `about`, `scope.project`, `sources[].edition`, `edition_of` отобранных записей;
- связи, у которых оба конца в подборке (с `retired_at`, если есть);
- записи объектов (`object`, `object_version`, `object_path`, итоги `source`) для всех источников подборки — без файлов;
- пакеты, которым принадлежат коды записей: `kind`, `entity_class`, `rel`, `selector_type`, `property` → владелец из `concept.origin`; понятия `origin = 'agent'` (величины, добавленные агентами) выгружаются в `concepts.jsonl`.

По выбору: `with_files` — файлы версий объектов из OCFL по digest; `with_history` — все ревизии записей, а не только текущая; `with_packs` — копии папок пакетов (находятся через `packs.discover()`; digest папки обязан совпасть с `pack.digest` в базе, иначе отказ).

### 4.2. Формат `amem.bundle/1`

Папка (или zip с той же структурой):

```
manifest.json      формат, created_at, base_id, agent, selection, packs [{name, version, digest, requires}],
                   counts, parts {имя файла: sha256}, with_files, with_history, amem_version
entities.jsonl     по записи на строку: id, key, entity_class, status, revision {n, content_hash, payload, agent,
                   recorded_at, review_state}, history [...] при with_history
atoms.jsonl        так же; payload — каноническое тело ревизии (ссылки по UUID, источники с object/version/digest)
links.jsonl        id, rel, src, dst, note, qualifiers, confidence, created_at, agent, retired_at
objects.jsonl      id, kind, original_name, media_type, url, retrieved_at, logical_paths, versions, статус
sources.jsonl      итоги сверки: revision_id, порядок, verdict, page — чтобы получатель не терял значки
concepts.jsonl     понятия origin = 'agent', которыми пользуются записи
objects/sha256/<hex>   файлы (with_files)
packs/<name>/      копии пакетов (with_packs)
```

Манифест пишется последним; `parts` даёт sha256 каждого файла, `bundle.inspect(folder)` сверяет их и показывает состав без базы. Zip — та же папка, упакованная `zipfile` без сжатия файлов объектов.

Приватное в подборку не попадает само: `scope.visibility` записей сохраняется, но отбор по умолчанию **исключает** `visibility: private`; `include_private=True` — явно.

### 4.3. Импорт

```python
bundle.import_(conn, store, folder, *, agent, trust="keep", dry_run=False) -> Imported
```

Порядок:
1. **Манифест и части.** `format`, sha256 частей, версия формата. Несовпадение — отказ до любого чтения базы.
2. **Пакеты.** Каждый пакет манифеста загружен в базу (`pack`) с тем же `name`, `version`, `digest`. Иначе — отказ со списком: что требуется, что есть; если в подборке лежат `packs/`, в ответе — путь, который нужно добавить в `AMEM_PACKS` и выполнить `prepare`. Автоматически пакеты не ставятся: это настройка базы, а не данные.
3. **Понятия агентов** (`concepts.jsonl`): принимается только схема `property` (величины, которые добавляют агенты); отсутствующие вставляются с `origin = 'agent'`, существующие с другим содержанием — предупреждение, локальное остаётся. Понятия других схем (виды, классы, связи) — предупреждение без вставки: это словари пакетов, и подборка не должна обходить проверку пакетов шага 2.
4. **Разбор** тел — Pydantic в строгом режиме, уровень 1 автопроверки (коды, шаблоны, концы связей, UCUM). Ошибка уровня 1 — отказ всей подборки с отчётом `amem.check/1`.
5. **Объекты.** Записи объектов по id: нет — вставка с тем же id и версиями (без файла версия помечается `no_file` в своих источниках, пока файл не придёт); есть — версии сверяются по digest, новые версии добавляются, расхождение digest одной и той же версии — отказ. Файлы `with_files` раскладываются в OCFL `objects.adopt(record, version, path)`; существующие по digest не копируются. Объект, известный базе под другим id, — тот же источник: файл — по digest версий, страница сайта и переписка — по адресу или названию; ссылки тел переводятся на локальные объект и версию (предупреждение), `origin_revision_hash` остаётся хэшем тела подборки как есть. Совпадение частичное — не найдена версия, на которую ссылается источник, или версии ведут на разные локальные объекты — отказ `bundle_object_conflict`. Отметка «что атомизировано» (`object_status`) переносится, если локальной нет, — агентом импорта; кто и когда отметил в базе-источнике — в заметке.
6. **Записи** — одна транзакция, один `changeset` с `reason = "import <base_id> <created_at>"`, порядок как в `records.commit`. Для каждой записи:

| Локально | Действие |
|---|---|
| Записи с таким id нет | создаётся с тем же id (новый параметр `records.commit(…, keep_ids=True)`), ревизия 1 локально; `provenance` = `{origin_base, origin_revision_hash, origin_agent}` |
| Есть, и любая локальная ревизия (текущая, ждущая, отклонённая, прежняя) совпадает: её `content_hash` или `provenance.origin_revision_hash` равен хэшу тела подборки или того же тела без полей происхождения | ничего — это содержание база уже видела: повтор подборки не переспрашивает о решённом (отклонённом) и не тянет назад то, от чего запись ушла; подборка, вернувшаяся без правок (A → B → A), совпадает по телу без `provenance` |
| Есть, отличается | новая ревизия с `review_state = pending`, пункт очереди `imported`; текущая не меняется |
| Есть с другим `key`, или `key` подборки занят другой записью | отказ до записи, список коллизий |
| Локальная запись `deprecated` / `superseded` | пропуск с предупреждением: решение о выводе из оборота — локальное |

`provenance` — часть тела, поэтому хэш импортированной ревизии отличается от хэша в подборке; именно для этого хранится `origin_revision_hash`: повторный импорт той же подборки ничего не меняет. Подборка, вернувшаяся в свою базу (`origin_base` равен локальному `base_id`), обрабатывается по тем же правилам — `provenance` не дописывается.

`with_history`: ревизии старше текущей **не** вливаются как ревизии (локальная история — локальная); они сохраняются в таблице `import_history` (id записи, ревизии подборки как есть) для просмотра. Это честнее, чем подделывать локальную историю.

7. **Статусы.** `trust=keep`: статус из подборки сохраняется, `review_state` новых ревизий — `none`; исключение — проверенное (`verified`, `auto_verified`) при импорте не человеком: модель не может сделать запись проверенной в этой базе, даже чужой проверкой, — `needs_review` и пункт `imported`, исходный статус — в `details` пункта; `trust=review`: все созданные записи и ревизии — `needs_review`, пункт `imported`. Пункты очереди ставятся так же, как в `submit`; `source_changed` — если источник ссылается не на последнюю локальную версию объекта.
8. **Связи.** По id — и тогда `rel` и концы обязаны совпасть (иначе id занят другой связью: отказ `bundle_key_collision`); действующая связь с теми же `rel`, `src`, `dst` уже есть — пропуск; `retired_at` в подборке и действующая локально — вывод из оборота с причиной «импорт»; локально выведена, в подборке действующая — остаётся выведенной (предупреждение).
9. **Итоги сверки** у созданных ревизий — своей сверкой, не верой подборке: есть копия файла версии — место и цитата сверяются уровнем 2 (`level2.judge_source`) по тексту копии; файла нет — `no_file`, пока файл не придёт; страница сайта и переписка — `external`. Итоги `sources.jsonl` не переносятся: чужой вердикт — утверждение, которое здесь не проверено, а `no_file` честнее значка, который нельзя подтвердить; часть остаётся в подборке для просмотра. Атом, место которого своя сверка не подтвердила (`fuzzy`, `not_found`, `no_file` у файлового источника), не остаётся `verified` / `auto_verified` / `draft`: `needs_review` и пункт `imported` с `details.verdicts` и `origin_status`; у ждущей ревизии — те же итоги в её пункте.

`dry_run=True` выполняет шаги 1–5 и уровень 1 без записи и возвращает план: сколько создаётся, совпадает, уходит на проверку, какие коллизии, отчёт уровня 1. Ответ `Imported`: `changeset_id`, счётчики по действиям, `queued`, `warnings`, `collisions` (у `dry_run` — вместо отказа), `report` (amem.check/1 уровня 1), `complete`. Отказ — `BundleError` с `code` (`bundle_pack_missing`, `bundle_key_collision`, `bundle_object_conflict`) и `details`.

### 4.4. Файлы-источники: где лежат и как переносятся

Хранилище копий уже есть и устроено как у Zotero, только строже: корень OCFL (`amem/ocfl_store.py`), один объект — один документ, версии — состояния файла, дайджест sha256; содержимое, которое уже лежит в объекте, второй раз не копируется; `objects.ingest` берёт файл из папки документов пользователя и копирует его в корень один раз. Подборка переносит файлы по `with_files` (разд. 4.1) или идёт без них — только записи; получатель без файла видит у источника `no_file`, пока файл не придёт (разд. 4.3, шаг 5).

Что фиксируется этой спецификацией для сервера (подпроект 4) и установщика:
- два каталога, оба — настройки, не данные: `AMEM_DOCS` — папка документов пользователя, откуда берутся файлы (читается), `AMEM_OBJECTS` — корень хранилища копий (пишется). Они разные: папка документов — чужая и живёт своей жизнью, корень хранилища принадлежит amem;
- в Docker оба каталога — **bind-монтирования папок хоста**, не именованные тома: корень хранилища человек должен видеть, копировать и бэкапить обычными средствами, как папку `storage` у Zotero; папка документов монтируется только для чтения. Пример в compose: `./data/objects:/var/lib/amem/objects` и `${AMEM_DOCS}:/docs:ro`;
- база хранит у объекта `logical_paths` (путь в папке документов) и digest, а не абсолютный путь хоста: при переезде папки документов ничего не ломается, копия в хранилище остаётся источником истины;
- ssearch и другие читатели файлов работают по той же папке документов независимо от amem; amem не требует, чтобы файлы лежали у него, и не требует ssearch — их связь остаётся контрактом подпроекта 6.

Проверка: `backup.snapshot` уже связывает дамп и хранилище по `base_id`; подборка с `with_files` раскладывает файлы по digest и принимается `objects.adopt`.

## 5. Записи человека

Политика статусов (`check.submit`, разд. 7.1 спецификации автопроверки) дополняется строкой: **агент `person:`** — новая запись и новая ревизия своей или чужой записи получают `verified`, `review_state = none`, пунктов очереди нет, риск шаблонов не применяется, уровень 5 не нужен. Уровни 1–2 выполняются полностью: ошибка схемы, неизвестный код, ненайденная цитата отклоняют пакет человека так же, как пакет модели — иначе база перестанет быть проверяемой. Предупреждения уровней 2–4 в отчёте остаются (человек их видит), на статус не влияют.

Исключение из «пунктов очереди нет» — `source_changed`: если пакет человека ссылается на не последнюю версию объекта, пункт ставится, потому что это вопрос о файле, а не проверка записи.

Две оговорки. Тело человека, совпавшее с ждущей ревизией или черновиком модели (`created = false`), новой ревизии не даёт и статус не меняет: черновик модели подтверждается через очередь. После прямой правки человеком старая ждущая ревизия модели остаётся `pending` без пункта: её пункт `edit` закрыт как устаревший, текущей она уже не станет.

Правка моделью записи, у которой текущая ревизия принадлежит человеку или имеет статус `verified`, — `pending`, как сейчас. О такой правке решает пункт `edit` по состоянию ревизии (`pending`), а не по статусу записи: у записи человека статус может быть и не `verified` (запись до 3c, `needs_review`, поставленный вручную); решение статус записи не меняет. Отвергнутая запись (`rejected`) открытых пунктов не держит, поэтому её правка моделью не ждёт, а проверяется обычным путём. Человек правит текст (`summary_plain`, `body`, `label`) обычной новой ревизией через `submit`; интерфейс для этого — подпроекты 4 и 5.

Личная заметка без объекта: `kind: note`, `basis: author`, `about` пуст, теги — свободно. Заметка о вещи — с `about`. Все остальные виды человек тоже может писать сам, с источником или с `basis`.

## 7. Приёмка

Пакеты и ядро:
- пакет с `requires` на отсутствующий или неподходящий по версии пакет — `PackError` с именами и версиями; цикл зависимостей — ошибка с цепочкой; порядок загрузки топологический (тест на трёх пакетах);
- `broader` на несуществующий код — ошибка загрузки;
- ядро 1.2.0: `note`, `artifact`, `bbox` есть; `has_source` 1.1.0 с `skip_if_set`; шаблон `note` требует `body` как `warning`;
- шаблон с `parameters` и неизвестной величиной, неизвестным `origin`, не-UCUM `default.unit`, повтором `property` или `target: atom` — ошибка с файлом.

Схема и проверка:
- `basis: author` от `model:` — `violation`; `basis: default` без `derived_from` — `warning`; `confidence` у `person:` — `violation`; `confidence: 0.5` при `high_risk: [low_confidence]` — `needs_review` и пункт `high_risk`; без правила — `draft`;
- атом `person:` без источника и с `basis: author` проходит и получает `verified` без пунктов очереди; тот же атом без `basis` — отклонён `has_source`;
- правка моделью атома человека — `pending`;
- `gen_schema.py --check` чист; старые примеры `tests/v1_examples` проходят без изменений.

Профиль и карточка:
- сведение `parameters` по `extends`: потомок заменяет правило предка с той же величиной, порядок — предки, затем свои;
- `atom_property` совпадает с построчным разбором после записи и после `rebuild_projections`;
- карточка: состояния `missing`, `asked`, `na`, `conflict`, `known` с `preferred`, `known` с `basis: default`; `by`, `source_role`, `confidence` в поле; `extra` у сущности без профиля; `ancestors` по `part_of` с обрывом цикла; сводка блокеров. Карточка «на момент» — не в этом подпроекте (нет выбора ревизии атомов на момент; отложено до интерфейса истории).

Подборки:
- экспорт по тегу, по проекту (включая `part_of`-достижимые сущности), по явным ссылкам; замыкание сущностей и связей; `private` исключено по умолчанию; `with_files` раскладывает файлы по digest; `with_packs` отказывает при несовпадении digest папки и базы; `inspect` ловит подмену части;
- импорт в пустую базу: все id сохранены, `provenance` заполнен, статусы по `trust`; повторный импорт — ничего не меняется (`counts.unchanged` равно числу записей);
- импорт при расхождении — новая ревизия `pending`, пункт `imported`, текущая не изменилась; коллизия `key` — отказ до записи; отсутствующий пакет — отказ с перечнем и подсказкой пути; `dry_run` — план без записи;
- связи: дубль пропущен, вывод из оборота перенесён; объекты: версии сверены по digest, файлы приняты `adopt`; `backup.create` считает новые таблицы;
- всё — на PostgreSQL 18 и 16.

## 8. Риски

| Риск | Что делаем |
|---|---|
| Профили разрастутся в формы с условной логикой | `when` — только текст; условия и вывод значений остаются у потребителя карточки. Пересмотр — после второго домена |
| `basis` начнут ставить вместо поиска источника | `default`/`assumed` без `derived_from` — предупреждение и человек; `author` доступен только человеку |
| Чужой `verified` сойдёт за свой | `provenance` виден в карточке и выдаче; `trust=review` для чужих баз; статус по умолчанию сохраняется осознанно — иначе обмен обесценивается |
| Импорт создаст дубли записей с разными id | Уровень 4 при импорте не выполняется (объём); дубли по ключу — отказ, по смыслу — обычная очередь `duplicate` отдельным проходом позже |
| Подборка без файлов теряет проверяемость | Итоги сверки переносятся, источники помечены `no_file` до появления файла; `with_files` — для серьёзного обмена |
| Проекция `atom_property` разойдётся с телами | Единый `_refresh`, `rebuild_projections`, тест-сверка — как у `atom_about` и поиска |
