# amemo — укрепление: слабые места кода и процесса

Редакция 1 (09.11.2026). Не подпроект, а очередь небольших задач, которые делаются между подпроектами и внутри них. Основание — разбор состояния `main` после слияния части 4a: 12,7 тыс. строк Python, 15,8 тыс. строк веба, 893 теста за 11 минут CI, девять миграций.

## Что уже сделано этим PR

- CI: на pull request тесты идут только на PostgreSQL 18, обе версии — на push в `main`; скачивание клиента PostgreSQL с повторами (`curl --retry`, три попытки `apt-get`); шаг `ruff check`.
- `ruff` в зависимостях разработки, правила `F` (pyflakes) и `E9` (синтаксис), `amemo/model_v1.py` исключён как сгенерированный. Найденные неиспользуемые импорты убраны.
- `tools/readme_assets.py` использовал синтаксис f-строк Python 3.12 при `requires-python >= 3.11` — исправлено.
- `tools/hooks/pre-push` — проверка диффа на приватное по списку образцов **вне репозитория** (`~/.config/amemo/private-patterns.txt` или `AMEMO_PRIVATE_PATTERNS`). Включается `git config core.hooksPath tools/hooks`. Сам список в репозиторий не попадает никогда.

## Чего не делаем

- Переписывать слой данных под ORM: объём SQL (около 250 запросов) и его характер (окна, `jsonb`, рекомендательные блокировки, триггеры) ORM не упростит.
- Менять JSONB-тело на колонки: ревизии с каноническим хэшем — основа модели, проекции при нём дешевле, чем нормализация.
- Переделывать CI на матрицу машин: две базы на одной машине быстрее и дешевле.
