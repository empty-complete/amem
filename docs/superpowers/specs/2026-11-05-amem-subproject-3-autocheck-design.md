# amem — подпроект 3: автопроверка и очередь проверки

Редакция 1 (05.11.2026), с правками по ревью спецификации: отчёт пакета не содержит очереди; статус меняется только у созданной ревизии; общий порядок блокировок; повторная сверка, плавающая доля аудита и метрика калибровки перенесены на потом; подпроект разделён на части 3a и 3b.

Продолжение спецификации схемы v1 (раздел об автопроверке) и подпроекта 2 (`2026-11-03-amem-subproject-2-engine-design.md`). Учтены уроки Graphiti и Graphify:
- ответ «принято» при обработке, которая ещё стоит в очереди, вводит в заблуждение (getzep/graphiti#1574);
- исходы проверки машиночитаемы;
- любое ослабление проверки объявляется в ответе.

## Цель

Одна точка записи знаний — `check.submit`. Пакет предложенных атомов, сущностей и связей проходит уровни 1–4. Пакет с ошибкой отклоняется целиком, и агент получает отчёт. Иначе пакет записывается: записи получают статусы, источники — итоги сверки с файлом, очередь проверки — пункты. Очередь наблюдаема: у пункта есть состояние, у очереди — метрики. Ответ записи разделяет то, что уже сделано, и то, что только поставлено в очередь.

Состав подпроекта:

**Часть 3a — проверка и запись** (отдельный PR):
- уровни 1–4 спецификации v1: схема и шаблон, привязка к источнику, здравый смысл, дубли;
- извлечение текста xlsx/xlsm и docx, сброс старого кэша «текста нет» у этих файлов;
- `submit`: статусы, итоги сверки в `source`, постановка пунктов очереди;
- таблицы очереди и вердиктов.

**Часть 3b — очередь** (отдельный PR):
- захват с арендой и решение с журналом вердиктов `verification`;
- выборка аудита;
- метрики;
- пересмотр при новой версии объекта.

Результат — библиотека `amem`, миграция `0006_check.sql` и тесты на PostgreSQL 18 и 16.

Что не входит в подпроект:
- **исполнитель уровня 5** — навык смыслового проверяющего и его ночной запуск: подпроект 4;
- **сервер MCP/HTTP и CLI**: подпроект 4;
- **страница «Проверка»**: подпроект 5.

Для них здесь готовы очередь, захват и функции решения.

## Решения

| Вопрос | Решение |
|---|---|
| Где проверка | Пакет `amem.check`. `records.commit` остаётся низкоуровневой записью без проверок — для миграций данных и тестов |
| Ошибка уровня 1 или 2 | Пакет отклоняется целиком: `records.reject` с отчётом. Копии файлов и новые версии объектов, принятые разбором источников, остаются — как в 2.2: копия — содержимое, а не утверждение. Пункты `source_changed` от этих версий — тоже |
| Новый атом | `needs_review`, если есть предупреждение или высокий риск. Иначе `draft` и пункт `semantic` в очереди — ждёт уровня 5 |
| Сущность | Уровни 1, 2 (источники — с важностью не выше предупреждения) и 4. Без предупреждений и риска — `auto_verified` и выборка аудита. Иначе `needs_review` |
| Тело совпало с текущей ревизией | Статус и очередь не меняются, обновляются только итоги сверки |
| Правка записи, проверенной человеком | Ревизия ждёт решения (`review_state = pending`), текущей не становится; пункт `edit` |
| Правка выведенной из оборота записи | Ошибка `retired_record`: сначала вернуть статус |
| Высокий риск | Правила `high_risk` в шаблонах пакетов (`always`, `numeric`); противоречие уровня 3 и сомнение уровня 5 — всегда. Ядро помечает так вид `decision` |
| Единицы | Грамматика UCUM и перевод через `ucumvert` (MIT) на pint 0.25. Минимальный Python — 3.11 |
| xlsx | `openpyxl`: лист — страница, числа — как их показывает формат ячейки |
| docx | Стандартная библиотека; страницы — по разрывам страниц, в том числе сохранённым Word |
| Дубли | Полнотекстовый поиск по словам подписи и вектор активной модели, если провайдер доступен. Пороги — константы до калибровки в пилоте |
| Очередь | `review_item`: причина, состояние `queued → claimed → done` или `obsolete`, аренда. Вердикты — неизменяемая таблица `verification` |
| Кто решает | `semantic` — любой агент, кроме автора пакета. Остальные причины — только `person:`; свою правку человек вправе подтвердить сам (один человек — тоже база) |
| Аудит | Постоянная доля 2 % записей, перешедших в `auto_verified`. Повышение доли по ошибкам — после пилота, когда будут данные |
| Ответ записи | `complete` — сделано ли всё. `queued` — что поставлено в очередь. Уровни — `done`, `queued`, `skipped` или `not_applicable` |
| Порядок блокировок | Везде одинаковый: агент → общая блокировка объектов (разделяемая) → записи по возрастанию id → пункты очереди и строки `source` |
| Сеть | Не нужна: уровень 4 выбирает провайдера как рецепты подпроекта 2, без провайдера идёт только текстом и объявляет это |

## 1. Устройство

| Модуль | Что делает |
|---|---|
| `amem/check/__init__.py` | `submit`, `Proposal`, `Submitted`, `CheckError` — порядок уровней, статусы, запись |
| `amem/check/report.py` | `Issue`, `Report`, перечень кодов, отчёт формата `amem.check/1` |
| `amem/check/templates.py` | Активные шаблоны, сведение, `Rules` |
| `amem/check/level1.py` … `level4.py` | Уровни проверки |
| `amem/check/numbers.py` | Числа атома и числа во фрагменте текста |
| `amem/check/units.py` | UCUM: проверка кода, перевод величины |
| `amem/extract.py` | Текст xlsx/xlsm и docx; `sources.extract_pages` передаёт ему эти файлы |
| `amem/review.py` | Постановка (3a); захват, решение, аудит, метрики, пересмотр при новой версии (3b) |
| `amem/sql/0006_check.sql` | Таблицы очереди и вердиктов, активные шаблоны, сброс кэша |

`sources.py` по-прежнему не знает о базе, `objects.py` по-прежнему пишет объекты отдельной транзакцией до пакета изменений.

### 1.1. Порядок `submit`

```python
check.submit(conn, store, docs, proposals, links=(), *, agent, activity=None, reason=None,
             provider=None) -> Submitted
```

`Proposal(target, payload, record_id=None)` — предложенная ревизия: новая запись, если `record_id` нет, иначе новая ревизия существующей. Статус агент не предлагает: его ставит автопроверка.

1. **Разбор.** Тело проверяется Pydantic в строгом режиме JSON: `AtomPayload`, `EntityPayload`, `LinkPayload`. Это часть уровня 1. Если тело не разобралось, остальные уровни для этой записи не идут.
2. **Ссылки.** Сопоставляются @имена пачки, ключи и UUID существующих записей: вид, класс, статус. Это нужно правилам шаблонов и концам связей. Неизвестная ссылка — `ref_unknown`.
3. **Уровень 1** — коды словаря, шаблоны, жёсткие правила, концы связей, UCUM (разд. 3).
4. **Уровень 2** — разбор источников в объекты, версии, текст, сверка цитаты и чисел, подстановка редакции (разд. 4).
5. **Есть хоть одна ошибка (`violation`)** — `records.reject` с отчётом, ответ `rejected`. Уровни 3 и 4 не выполняются.
6. **Уровни 3 и 4** — только у пакета без ошибок (разд. 5, 6).
7. **Запись — одна транзакция** (разд. 7.5).
8. **Ответ** `Submitted` (разд. 2.3).

Поздний отказ `records.commit` (ключ занят, сроки редакций пересекаются) откатывает транзакцию. Затем пакет записывается отклонённым с кодом `record_error` — вызовом `records.reject` уже после отката, вне внешней транзакции.

Ошибки окружения не превращаются в отклонённый пакет: в базе ничего не появляется (кроме объектов, принятых в шаге 4), исключение уходит вызывающему. Это:
- `StoreError` — нет корня хранилища или пропала копия версии;
- сбой соединения с базой;
- `EmbeddingError` от явно переданного провайдера.

Уровни 1–4 читают базу вне транзакции записи. Два параллельных пакета с одинаковым атомом оба могут пройти уровень 4 без предупреждения — это допустимо. Уровни 1 и 2 опираются на неизменяемые объекты и версии и на редко меняющиеся словари и шаблоны. Статус существующей записи решает политику правки, поэтому он перечитывается под блокировкой — уже в транзакции записи.

## 2. Отчёт и исходы

### 2.1. Замечание

`Issue(level, severity, code, where, message, details)`:
- `level` — 1–4;
- `severity` — `violation`, `warning` или `info` (перечень `Severity`);
- `code` — из закрытого перечня `CheckCode` схемы;
- `where` — метка записи (`@имя`, `items[i]`, `links[i]`) и путь поля, например `@a1: sources[0].quote`;
- `message` — по-русски, для человека;
- `details` — JSON для машины: точный текст документа, кандидаты, ненайденные числа.

### 2.2. Коды

| Код | Уровень | Важность | Когда |
|---|---|---|---|
| `schema` | 1 | violation | Тело не проходит Pydantic; `details.loc`, `details.msg` |
| `unknown_code` | 1 | violation | Нет кода `kind`, `entity_class`, `rel` или типа селектора в загруженных пакетах |
| `ref_unknown` | 1 | violation | Ссылка на запись, которой нет |
| `template` | 1 | из правила | Не выполнено правило поля; `details`: шаблон, путь правила, вид правила |
| `ucum` | 1 | из правила | Единица — не код UCUM |
| `unit_required` | 1 | violation | Есть `amount` или границы, нет `unit` |
| `bounds_order` | 1 | violation | `lower_bound` больше `upper_bound` или `amount` вне границ |
| `link_not_allowed` | 1 | violation | Исходящая связь вида, которого нет в `links.allowed` |
| `link_required` | 1 | из правила | Нет обязательной связи шаблона |
| `link_pair` | 1 | violation | Концы связи не из `pairs` её вида |
| `retired_record` | 1 | violation | Правка записи со статусом `deprecated` или `superseded` |
| `record_error` | 1 | violation | Поздний отказ `records.commit` |
| `source_unresolved` | 2 | violation | Путь источника не разобрался (`ObjectError`) |
| `version_missing` | 2 | violation | У объекта нет указанной версии |
| `digest_mismatch` | 2 | violation | `digest` не совпадает с версией |
| `pdf_page_required` | 2 | violation | У источника атома из PDF нет селектора страницы |
| `pdf_quote_required` | 2 | violation | У источника атома из PDF нет цитаты или она короче `sources.MIN_QUOTE` |
| `quote_not_found` | 2 | violation; warning у сущности | Цитата задана, но в тексте её нет |
| `quote_fuzzy` | 2 | violation; warning у сущности | Цитата найдена только нечётким поиском; `details`: точный текст, страница, схожесть |
| `number_not_found` | 2 | violation или warning | Числа атома нет во фрагменте (разд. 4.5) |
| `page_moved` | 2 | info | Цитата на другой странице — номер исправлен в `source.page` |
| `place_unresolved` | 2 | warning | Цитата не задана, и место не найдено |
| `no_text` | 2 | warning | У файла нет текста: скан, чертёж, неподдерживаемый формат |
| `external_source` | 2 | warning | Источник — страница сайта или переписка |
| `source_error` | 2 | warning | Сбой извлечения или сверки |
| `numbers_unchecked` | 2 | info | Числа не с чем сверить: ни у одного источника нет фрагмента |
| `edition_filled` | 2 | info | Редакция подставлена по файлу |
| `unknown_property` | 3 | warning | Кода величины нет в словаре `property`, хотя словарь величин загружен |
| `out_of_range` | 3 | warning | Значение вне `plausible_min` – `plausible_max` величины |
| `unit_mismatch` | 3 | warning | Единицу значения нельзя перевести в единицу величины |
| `conflict` | 3 | warning | Другое значение той же величины у той же сущности при тех же условиях — кандидат в `contradicts` |
| `duplicate` | 4 | warning | Похоже на существующую запись или на запись этой же пачки — кандидат в слияние или `same_as` |
| `related` | 4 | info | Похожие записи ниже порога дубля — подсказка для связей |

### 2.3. Отчёт и ответ

Отчёт пишется в `changeset.check_report` до записи ревизий и потом не меняется (`changeset_immutable`). Поэтому в нём только то, что известно до записи: уровни, замечания, ослабления, применённые шаблоны и для каждой записи — плановый статус и риск.

```json
{"format": "amem.check/1",
 "levels": {"1": "done", "2": "done", "3": "done", "4": "done"},
 "issues": [{"level": 2, "severity": "info", "code": "page_moved", "where": "@a1: sources[0]",
             "message": "Цитата найдена на странице 12, а не 11", "details": {"page": 12}}],
 "degraded": [{"level": 4, "channel": "vector", "reason": "backend_disabled"}],
 "templates": ["has_label@1.0.0", "has_source@1.0.0", "has_value@1.0.0"],
 "records": [{"label": "@a1", "target": "atom", "planned_status": "draft", "risk": []}]}
```

Уровни 3 и 4:
- отклонение после уровня 1 или 2 — `skipped`, `records` в отчёте нет;
- `record_error` — `done`: они успели выполниться.

Пункты очереди лежат в `review_item` (у пункта есть `changeset_id`) и в ответе.

Ответ `Submitted`:
- `state` — `approved` или `rejected`;
- `changeset_id`, `report`;
- `records` — метка, вид, `record_id`, `revision_id`, `created`, итоговый `status`, `review_state`;
- `queued` — поставленные пункты: id, причина, метка, `record_id`;
- `levels` — уровни отчёта и уровень 5:
  - `queued` — поставлен хоть один пункт `semantic`;
  - `not_applicable` — в пакете нет атома, получившего `draft`: только сущности и связи, или все атомы ушли к человеку;
  - `skipped` — пакет отклонён;
- `complete` — `true`, только если в очереди ничего не появилось.

Обычный пакет атомов возвращает `complete: false` и `levels["5"] = "queued"`, и это намеренно.

## 3. Уровень 1 — схема и шаблон

### 3.1. Коды словаря

`kind`, `entity_class` и `rel` ищутся в `concept` по своей схеме. Тип каждого селектора — с цепочкой `refined_by` — ищется в схеме `selector_type`. Нет кода — `unknown_code`. Коды величин проверяет уровень 3.

### 3.2. Шаблоны

Действуют только активные шаблоны: `template_active` хранит версию каждого кода из загруженных сейчас пакетов (разд. 10). Шаблон пакета, который больше не загружается, не действует, хотя строка в `template` остаётся.

Набор шаблонов записи:
- все интерфейсы её `target` (`applies_to` пуст) по возрастанию кода;
- затем шаблон её кода (`applies_to` = `kind`, `entity_class` или `rel`).

Каждый шаблон раскрывается: сначала его `extends` слева направо (рекурсивно), затем собственные правила. Шаблон, уже применённый раньше в этом наборе, повторно не применяется.

Сведение:
- правила полей сводятся по `path`: правило, применённое позже, заменяет прежнее с тем же путём. Так потомок заменяет предка, а из двух несвязанных интерфейсов действует тот, чей код больше;
- `links.allowed` — действует последний в порядке применения шаблон, который его задаёт;
- `links.required` сводится по `rel` тем же правилом;
- `high_risk` объединяется.

Отчёт перечисляет применённые шаблоны как `code@version`.

**Правила полей** (`FieldRule`). Путь — через точку; `[]` у промежуточного поля значит «каждый элемент списка». Замечание называет конкретный элемент: `sources[1].selectors`.
- `required` — поле непустое:
  - список — хотя бы один элемент;
  - `LangString` — непустой `ru`;
  - объект — хотя бы одно непустое поле;
  - строка — не пустая и не из одних пробелов.
- `min_count` — в списке не меньше N элементов.
- `selector_types` — хотя бы один селектор из перечня с учётом цепочки `refined_by`. Путь ведёт на список селекторов или на источник — тогда берутся его селекторы.
- `entity_classes` — ссылка по пути ведёт на сущность одного из классов; @имя пачки берёт класс из своего тела.
- `ucum` — значение по пути, если оно есть, — код UCUM (разд. 3.5).

Важность — из правила, по умолчанию `violation`. Текст замечания — `message` правила или общий.

**Правила связей** (`LinkRules`):
- `allowed` — исходящая связь записи другого вида даёт `link_not_allowed`;
- `required` — хотя бы одна связь этого вида, а при `to_classes` — к сущности одного из этих классов; иначе `link_required`.

Связи считаются вместе: действующие связи записи в базе, связи пачки и поля, через которые выражается вид связи (`via_field` у понятия: `about`, `derived_from`). Симметричная связь — исходящая с обоих концов. Уже записанные связи учитываются только для `required`: на `allowed` они не перепроверяются, иначе любую правку блокировали бы старые данные.

Связь пачки с видом, который выражается полем (`about`, `derived_from`), — `link_not_allowed` с местом `links[i]: rel`: такой вид пишется полем тела, а не связью, и `records.commit` отверг бы её поздно.

**Высокий риск.** Шаблон может задать `high_risk` — список правил из закрытого перечня `HighRiskRule`:
- `always` — каждая запись этого вида;
- `numeric` — атом, в котором есть числа из разд. 4.5.

Ядро получает шаблон `decision` с `high_risk: [always]`; версия пакета ядра — 1.1.0.

### 3.3. Жёсткие правила

Что шаблоном не выразить, проверяется всегда — для каждой величины и уточнения:
- есть `amount`, `lower_bound` или `upper_bound` — нужна `unit` (`unit_required`); безразмерная величина — `1`;
- `lower_bound ≤ upper_bound`, и `amount`, если задан, лежит в границах (`bounds_order`).

### 3.4. Концы связей

У каждой связи пачки пара видов концов (`atom>entity` и т. п.) должна входить в `pairs` её вида, иначе `link_pair`. Вид конца берётся из ссылки: `atm:` или `ent:`, у @имени — из пачки. Связь записи с самой собой — тоже `link_pair`. Две правки одной записи в пачке — `schema` у второй.

### 3.5. UCUM

Код проверяет грамматика UCUM из `ucumvert`, с учётом регистра. Код, который не разбирается, даёт `ucum` с важностью правила; у шаблона ядра `has_value` это `violation`.

Перевод в pint — отдельный шаг, он нужен только уровню 3. Верный код не всегда переводится: у `W/(m2.Cel)` смещённая шкала внутри произведения. Тогда уровень 3 даёт `unit_mismatch`, а уровень 1 код принимает.

Парсер и реестр pint создаются один раз на процесс, при первом обращении.

### 3.6. Проверка шаблонов при загрузке пакетов

Осмысленность шаблонов сейчас проверяют только тесты, и только у шаблонов, поставляемых с amem. Эти проверки переезжают в `packs.load_packs` и действуют для любого пакета из `AMEM_PACKS`:
- `extends` ведёт на шаблон того же `target`;
- в наследовании нет циклов;
- код `applies_to` есть в словарях загружаемых пакетов;
- пути правил ведут на настоящие поля схемы;
- коды в `selector_types` и `entity_classes` существуют;
- один `code` шаблона — не больше чем в одном пакете;
- одна пара (`target`, `applies_to`) — не больше чем у одного шаблона.

Ошибка — `PackError` с файлом шаблона.

## 4. Уровень 2 — привязка к источнику

Уровень 2 проверяет источники атомов и сущностей. У сущности:
- ошибки разбора, версии и `digest` остаются ошибками;
- замечания о цитате и месте — предупреждения;
- правила PDF и сверка чисел не применяются.

Источник сущности-документа — сам файл, страница и цитата ему не нужны.

### 4.1. Объект и версия

Источники разбираются по одному: `objects.resolve_sources(conn, store, docs, {"sources": [s]}, agent=…)`. Так одна ошибка не прячет другие.

У источника с `path`:
- `ObjectError` — `source_unresolved` с местом `sources[i]`;
- `StoreError` уходит вызывающему.

У источника с `object`:
- нет такой версии — `version_missing`;
- `digest` не тот — `digest_mismatch`.

### 4.2. Место в документе

Селекторы источника вместе с цепочкой `refined_by` дают ожидаемую страницу, диапазон страниц, локатор и цитату.

| Тип селектора | Что даёт |
|---|---|
| `page` | Число — ожидаемая страница (`sources.as_page`). Диапазон «24–25» или «24-25» — страницы фрагмента; ожидаемой страницы он не задаёт, и цитата ищется по всем страницам |
| `sheet` | Страница — номер листа xlsx с этим именем (имя листа — первая строка его страницы, разд. 9.1; сравнение NFC и без регистра). Имени нет — место не найдено |
| `table`, `clause`, `figure`, `formula`, `heading` | Локатор: `label`, иначе значение с приставкой — «табл. 11.1», «п. 5.2», «рис. 3», «формула (7)»; у `heading` — значение как есть |
| `text_quote` | Цитату, если поле `quote` пусто |
| `slide`, `range`, `lines`, `function` | Здесь место не уточняют |

Сверка — `sources.judge(DocText.of(pages), quote, page, locator)`. Текст — `objects.text`, кэш `object_text` по `digest`.

У `judge` одностраничный документ без цитаты — `ok`. Уровень 2 принимает это только для `.md` и `.txt`. У PDF, docx и xlsx без цитаты, локатора и листа итог — `unresolved`: docx без разрывов страниц и книга из одного листа — не повод считать место найденным.

### 4.3. Итоги и важность

Важность ниже — для атома; у сущности см. начало раздела.

| Случай | verdict | Замечание |
|---|---|---|
| Страница сайта или переписка | `external` | warning `external_source` |
| У файла нет текста | `no_text` | warning `no_text` |
| PDF без селектора `page` | — | violation `pdf_page_required` |
| PDF без цитаты или с цитатой короче `MIN_QUOTE` | — | violation `pdf_quote_required` |
| Цитата найдена на указанной странице | `ok` | — |
| Цитата найдена на другой странице | `moved`, `page` — где найдена | info `page_moved` |
| Цитата найдена только нечётко | — | violation `quote_fuzzy` с точным текстом документа |
| Цитата задана, но не найдена | — | violation `quote_not_found` |
| Цитата не задана, место найдено селектором | `by_locator` | — |
| Цитата не задана, место не найдено | `unresolved` | warning `place_unresolved` |
| Сбой извлечения или сверки | `error` | warning `source_error` |

PDF — объект с `media_type = application/pdf` или с именем на `.pdf` (регистр не важен).

У атома итоги `fuzzy`, `not_found` и `no_file` в строки `source` не попадают: такой пакет отклоняется раньше. У сущности `fuzzy` и `not_found` записываются вместе с предупреждением. Так это и описано в коде уровня 2.

### 4.4. Фрагмент

Фрагмент источника — страницы, где сверка нашла место:
- у `ok` и `moved` — страница цитаты;
- у `by_locator` — страница локатора;
- у одностраничных `.md` и `.txt` — их страница;
- у селектора `sheet` — лист.

К ним добавляются страницы диапазона селектора `page` («24–25»): так таблица, перешедшая на следующую страницу, сверяется целиком. У `external`, `no_text`, `unresolved` и `error` фрагмента нет.

### 4.5. Числа

**Числа атома:**
- `amount`, `lower_bound`, `upper_bound` у `content.values[]`;
- те же поля у `content.values[].qualifiers[]` и `qualifiers[]` атома — это числа условий;
- числовые ячейки `content.table.rows` — числа JSON; `true` и `false` числами не считаются.

У формул чисел для сверки нет.

**Числа фрагмента.** Из текста извлекаются все записи чисел:
- **разделители.** Десятичный — запятая или точка. Группы разрядов — через пробел, неразрывный или узкий пробел, только по три цифры.
- **запятая или точка перед ровно тремя цифрами** даёт два значения: «1,200» — это и 1.2, и 1200.
- **неоднозначные пробелы** дают все прочтения: «10 200» — и 10200, и 10 с 200.
- **знак.** Тире или минус (`-`, `−`, `–`, `‒`) перед числом:
  - стоит вплотную к цифре, а перед ним не цифра (начало строки, пробел после слова, скобка) — число отрицательное;
  - перед ним цифра, или между знаком и цифрой пробел («5–10», «5 – 10», «– 10») — даёт оба значения: и 10, и −10.
- **экспонента** — запись `1,5e-3`.

**Сравнение** — точное, со знаком: десятичная запись числа из JSON (`Decimal(str(x))`) против значений фрагмента.

**Итог.** Число найдено, если оно есть во фрагменте хотя бы одного файлового источника атома. Иначе — `number_not_found`, `details` перечисляет ненайденные числа. Важность:
- warning, если число — из уточнений (`qualifiers`): условия часто записаны в другом месте документа;
- warning, если у атома есть источник с `role: derived`;
- иначе violation.

Если фрагмента нет ни у одного источника — info `numbers_unchecked`.

Записи вида «1,5·10⁻³» и «1,2 тыс.» не разбираются. Пересчитанное агентом значение помечается `role: derived` — это записано в README.

### 4.6. Подстановка редакции

У источника атома нет `edition`, а версия его объекта — источник ровно одной текущей сущности класса `edition`. Тогда эта редакция подставляется в тело и пишется info `edition_filled`. Если подходящих редакций несколько, ничего не подставляется.

### 4.7. Запись итогов

Итоги пишутся в транзакции записи. Каждая строка `source` находится по ревизии и позиции, обновляются `verdict`, `page`, `anchor`, `checked_at`:
- `checked_at` — время пакета изменений (`changeset.created_at`);
- `page` — найденная страница;
- `anchor` — текст для подсветки.

Ревизия с телом, совпавшим с текущей (`created = false`), тоже получает свежие итоги. Тест следит, что каждое значение, которое пишет уровень 2, входит в `SourceVerdict`.

## 5. Уровень 3 — здравый смысл

Уровень 3 проверяет величины атомов (`content.values[]`).

**Словарь величин.** Понятия схемы `property` в пакетах задают `unit`, `quantity_kind`, `plausible_min`, `plausible_max`. Если в базе нет ни одного понятия `property`, коды величин свободны, и уровень 3 только сверяет атомы между собой. Если словарь величин загружен, неизвестный код даёт `unknown_property` — кандидат в новое понятие, его утверждает человек.

**Диапазон.** У величины словаря с границами `amount` и границы значения переводятся в единицу понятия:
- вне `[plausible_min, plausible_max]` — `out_of_range`;
- перевести нельзя (другая размерность или смещённая шкала) — `unit_mismatch`.

**Согласие.** Сравниваются атомы, у которых совпадает всё перечисленное:
- **сущность** — пересекаются множества `about`;
- **величина** — тот же `property`;
- **условия** — одинаковые множества уточнений атома и значения, после приведения JSON к канонической форме;
- **срок** — `valid_from` – `valid_to` пересекаются.

Если при этом значение другое, это `conflict` и риск `conflict`. «Другое» — после перевода единиц `amount` или границы различаются больше чем на 1e-9 относительно, либо различается `value_text`. `details.candidates` — атомы-соперники: `[{"ref": …, "suggest": "contradicts"}]`.

Соперники — текущие атомы со статусом `draft`, `needs_review`, `auto_verified`, `verified`, а также атомы этой же пачки. Поиск идёт через `atom_about` по сущностям атома, затем фильтруется в Python. Атом без `about` на согласие не проверяется.

## 6. Уровень 4 — дубли

**Атомы.** Кандидаты — текущие атомы того же вида со статусом `draft`, `needs_review`, `auto_verified` или `verified`, кроме самой записи. Каналы:
- **текст.** Собственный запрос уровня 4: `to_tsquery('simple', …)` из лексем `to_tsvector('russian', label)`, соединённых через `|` («любое из слов»), до 20 кандидатов. Схожесть — `rapidfuzz.fuzz.token_sort_ratio` нормализованных подписей: регистр, `ё → е`, без пунктуации. `search._fts` не подходит: в `websearch_to_tsquery` нет «или» через `|`.
- **вектор.** Доступность — как у рецептов (`recipes._availability`): активная модель и провайдер `embed.get_provider(provider)`. Вектор поискового документа тела (`search.search_text(...).document`) сравнивается со свежими векторами активной модели (`search._vector`), до 20 кандидатов; схожесть = 1 − cosine distance. Неявный провайдер создаётся один раз на процесс, чтобы модель не загружалась на каждый пакет.

Пороги — константы модуля, их калибрует пилот:

| Итог | Текст | Вектор | Сколько кандидатов |
|---|---|---|---|
| `duplicate` (warning) | ≥ 90 | ≥ 0,92 | все выше порога |
| `related` (info) | ≥ 60 | ≥ 0,80 | до 5 |

**Сущности.** Кандидаты — того же класса. Схожесть — лучшая пара среди подписей и `aliases`. `duplicate` предлагает `same_as`.

**Кандидаты в замечании** — в той же форме, что у `conflict` уровня 3: `details.candidates` — список `{ref, channel, score}`; у `duplicate` ещё `suggest` (`merge` у атома, `same_as` у сущности).

**Внутри пачки** атомы одного вида и сущности одного класса сравниваются попарно, текстом.

**Ослабление.** Без вектора — нет активной модели (`no_active_model`), `AMEM_BACKEND=none` (`backend_disabled`) или неявный провайдер отказал с `EmbeddingError` (`provider_error`) — работает только текст. Отчёт получает `degraded` с этой причиной. Вектора ищутся только среди записей, у которых они уже посчитаны; покрытие отдельно не считается. Журнал выдачи (`retrieval`) уровень 4 не пишет — это не поиск пользователя.

## 7. Статусы, риск и запись

### 7.1. Политика по статусу записи

| Запись | Ревизия | Статус |
|---|---|---|
| Новая | Текущая | Атом: `needs_review` при предупреждении или риске, иначе `draft`. Сущность: `needs_review` при предупреждении или риске, иначе `auto_verified` |
| `draft`, `needs_review`, `auto_verified`, `rejected` | Текущая | Как у новой |
| `verified` | Ждёт решения (`pending`); текущая не меняется | Не меняется |
| `deprecated`, `superseded` | — | Ошибка `retired_record` |
| Любая, тело совпало с текущей (`created = false`) | Новой нет | Не меняется, пункты не ставятся |

Предупреждение — замечание `warning`; `info` на статус не влияет. Риск — список строк: `template:<code>:always`, `template:<code>:numeric`, `conflict`; `<code>` — вид атома или класс сущности (правила риска сведены по всей цепочке шаблонов, применённые шаблоны перечислены в `templates` отчёта).

`records.commit` меняет статус существующей записи раньше, чем узнаёт, что тело не изменилось. Поэтому `submit` не передаёт `Item.status` существующим записям. Статус ставится после `commit` и только у ревизий с `created = true` — через `records.set_status_locked` в той же транзакции, запись уже заблокирована. Новым записям начальный статус передаётся через `Item.status`, как раньше.

### 7.2. Пункты очереди при записи

| Итог | Пункт |
|---|---|
| Атом `draft` | `semantic` — ждёт уровня 5 |
| Атом или сущность `needs_review` с риском | `high_risk` |
| Атом или сущность `needs_review` без риска | `warning` |
| Правка проверенной записи | `edit` |
| Сущность `auto_verified`, попавшая в выборку | `audit` |
| Источник ссылается не на последнюю версию объекта | `source_changed` (разд. 7.5, шаг 6) |

`details` пункта — коды замечаний записи, риск, кандидаты уровней 3 и 4.

### 7.3. Устаревание

Открытый пункт становится `obsolete`, когда его ревизия больше не та, о которой спрашивают:
- ревизия не текущая и не ждёт решения;
- или ревизия ждёт решения, но старше текущей — после неё принята более новая;
- или по записи принято итоговое решение человека (`verified` или `rejected`) — тогда остальные открытые пункты ревизии закрываются, кроме `source_changed`: новую версию файла решавший не видел, это отдельный вопрос;
- или запись получила статус `rejected`, `deprecated` или `superseded`.

Закрывается он:
- в транзакции записи — у записей, получивших новую ревизию;
- в транзакции решения — у той же ревизии;
- лениво при захвате и решении — всё, что изменилось мимо очереди.

### 7.4. Аудит

Аудит выбирает записи, перешедшие в `auto_verified`: сущность при записи, атом — после подтверждения уровня 5 (часть 3b).

Выборка детерминирована. Берутся первые 8 байт `sha256("amem-audit" ‖ revision_id)`, читаются как число и делятся на 2⁶⁴. Если результат меньше `AUDIT_RATE = 0.02`, запись идёт в аудит.

Повышенная доля для автора или типа файла с частыми ошибками аудита отложена до пилота: без данных её порог не на чем выставить. Метрики (разд. 8.7) уже считают долю `refuted` по авторам.

### 7.5. Транзакция записи

Общий порядок блокировок — для `submit`, решения и новой версии объекта: агент → разделяемая блокировка объектов → записи по возрастанию id → пункты очереди и строки `source`.

1. `INSERT INTO agent … ON CONFLICT DO NOTHING` — до любых блокировок. Иначе вставка нового агента после блокировки записи встаёт в тупик с параллельным пакетом того же нового агента.
2. `pg_advisory_xact_lock_shared(OBJECTS_LOCK)`. Новая версия объекта (`objects.ingest`, исключительная блокировка) и полный снимок (`backup.snapshot`) ждут пакетов, а пакеты — их. Без неё `ingest` мог бы не увидеть незафиксированную ревизию со ссылкой на старую версию.
3. Существующие записи блокируются `FOR NO KEY UPDATE` по возрастанию id — как в `records.commit`, поэтому тупиков нет. Статусы перечитываются, по ним выбирается политика 7.1. Если правка стала невозможной (`retired_record`), транзакция откатывается и пакет отклоняется.
4. `records.commit`: его `transaction()` — точка сохранения; правка проверенной записи — с `review_state = pending`.
5. Статусы созданных ревизий существующих записей (разд. 7.1).
6. Итоги сверки — `UPDATE source`: единственное изменение, которое разрешает триггер `amem_source_check`. Затем проверка версий: если источник ссылается на версию объекта меньше последней, ставится `source_changed` (под блокировкой из шага 2 новых версий не появится).
7. Устаревшие пункты закрываются, новые вставляются (`ON CONFLICT DO NOTHING` по индексу открытых пунктов), выборка аудита.

### 8.2. Причины

| Причина | Откуда | Кто решает | Исходы |
|---|---|---|---|
| `semantic` | Атом `draft` | Модель (кроме автора пакета) — все четыре исхода; человек — `confirmed`, `refuted` | см. 8.5 |
| `warning` | Предупреждения уровней 1–4 | `person:` | `confirmed`, `refuted` |
| `high_risk` | Риск записи | `person:` | `confirmed`, `refuted` |
| `semantic_doubt` | Уровень 5 не подтвердил | `person:` | `confirmed`, `refuted` |
| `edit` | Правка записи, проверенной человеком | `person:` | `confirmed`, `refuted` |
| `source_changed` | Ссылка на старую версию объекта | `person:` | `confirmed`, `refuted` |
| `audit` | Выборка аудита | `person:` | `confirmed`, `refuted` |
| `calibration` | Поставлен вручную | `person:` | `confirmed`, `refuted` |

Исключение автора действует только для `semantic`. Его смысл — модель не подтверждает свой же текст. Человек вправе подтвердить свою правку: в личной базе других проверяющих нет.

### 8.3. Состояния

```
queued ──claim──▶ claimed ──resolve──▶ done
  │  ▲               │
  │  └──release──────┤   (истёкшую аренду захватывают заново: claimed → claimed)
  └──────────────────┴──────────────▶ obsolete
queued ──resolve──▶ done              (решение без захвата — из карточки)
```

`done` и `obsolete` конечны.

### 8.4. Захват

```python
review.claim(conn, *, agent, reasons=None, limit=1, lease=timedelta(minutes=15), now=None) -> list[dict]
```

`claim` выдаёт самые старые пункты, которые агент вправе решать: в состоянии `queued` или `claimed` с истёкшей арендой. Пункт `semantic` не достаётся модели — автору его пакета; человек свои пункты получает (разд. 8.2). Выборка — `FOR UPDATE SKIP LOCKED`: параллельные проверяющие не берут один пункт. Записи `claim` не блокирует. Устаревший пункт (разд. 7.3) закрывается `obsolete` и не выдаётся.

Возвращённый пункт содержит:
- поля пункта;
- тело ревизии;
- источники с итогами сверки;
- автора пакета.

`review.release(conn, item_id, *, agent)` возвращает захваченный пункт в `queued`; вернуть может только тот, кто его держит.

### 8.5. Решение

```python
review.resolve(conn, item_id, outcome, *, agent, confidence=None, note=None, now=None) -> dict
```

Порядок блокировок — как у записи:
1. Пункт читается без блокировки — чтобы узнать запись.
2. Агент.
3. Запись — `FOR NO KEY UPDATE`.
4. Пункт — `FOR UPDATE`; состояние и права перепроверяются.

Проверки:
- пункт `queued`, либо `claimed` этим агентом, либо с истёкшей арендой;
- агент вправе решать причину, исход допустим;
- ревизия ещё актуальна (разд. 7.3). Если нет — пункт закрывается `obsolete`, и приходит `ReviewError`.

Затем пишется `verification`, пункт закрывается `done`, и применяются последствия. Каждое последствие срабатывает только при ожидаемом статусе записи; если статус уже другой (например, человек успел решить по другому пункту), вердикт записывается без смены статуса.

| Причина | Исход | Ожидаемый статус | Последствие |
|---|---|---|---|
| `semantic` (модель) | `confirmed` и `confidence ≥ SEMANTIC_MIN_CONFIDENCE` (0,8) | `draft` | `auto_verified`, выборка аудита |
| `semantic` (модель) | иначе | `draft` | `needs_review`, пункт `semantic_doubt` |
| `semantic` (человек) | `confirmed` / `refuted` | любой, кроме выведенных из оборота | `verified` / `rejected` |
| `edit` | `confirmed` / `refuted` | `verified` | `records.decide(accept=True / False)`; его `transaction()` — точка сохранения |
| Остальные | `confirmed` / `refuted` | любой, кроме выведенных из оборота | `verified` / `rejected` |

Итоговое решение человека закрывает остальные открытые пункты этой ревизии как `obsolete`, кроме `source_changed` (разд. 7.3). Статус меняется через `records.set_status_locked` с агентом решающего и причиной `review:<reason>`. Ответ — id вердикта, статус, новые пункты.

### 8.6. Ручная постановка

`review.enqueue(conn, ref, reason, *, agent, note=None)` ставит пункт на текущую ревизию записи:
- причины — `calibration` или `audit`;
- ставит только `person:`;
- открытый пункт с той же причиной не дублируется — возвращается его id.

### 8.7. Метрики

`review.stats(conn, *, days=7, now=None)` возвращает JSON:

| Раздел | Что внутри |
|---|---|
| `queue` | По причинам: `queued`, `claimed`, `expired` (аренда истекла), возраст самого старого `queued` в секундах |
| `done` | За окно, по причинам: число и медиана времени от постановки до решения; `obsolete` — отдельным числом |
| `changesets` | За окно: `approved`, `rejected`, частота кодов ошибок отклонённых пакетов |
| `records` | Атомы и сущности по статусам |
| `sources` | Строки `source` текущих ревизий по `verdict`; пустой итог — `unchecked` |
| `audit` | По авторам пакетов: решено пунктов аудита и сколько из них `refuted` |

`review.items(conn, *, state=None, reason=None, record=None, limit=100)` — список пунктов для интерфейсов.

### 8.8. Новая версия объекта

`objects.ingest` создаёт версию `n > 1` существующего объекта и в той же транзакции (под исключительной блокировкой объектов) вызывает `review.on_new_version(conn, object_id, n, *, agent, at)`.

Пункты `source_changed` получают текущие и ждущие решения ревизии атомов и сущностей, которые ссылаются на объект с версией меньше `n`: ждущая правка, принятая позже, иначе осталась бы со ссылкой на старую версию без пересмотра. Записи со статусом `rejected`, `deprecated` и `superseded` пропускаются. `details`: объект, старые версии, новая.

Открытый пункт той же ревизии не дублируется. Пакет, разобравший путь в старую версию до появления новой, ставит пункт сам (разд. 7.5, шаг 6). Пункт устаревает по общему правилу 7.3 — например, когда запись получает ревизию со ссылкой на новую версию.

## 9. Текст xlsx и docx

### 9.1. xlsx и xlsm

`openpyxl.load_workbook(read_only=True, data_only=True)`. Каждый лист книги, в её порядке, — страница. Первая строка страницы — имя листа, дальше строки листа:
- ячейки — через табуляцию;
- хвостовые пустые ячейки отброшены, пустые строки пропущены;
- скрытые листы входят.

Значение ячейки:
- **число — как его показывает Excel.** Формат с явным числом знаков (`0`, `0.0`, `0.00`, `#,##0.00`, `0%`, `0.00%`) — округление до этих знаков, у процентов — умножение на 100 и знак `%`. Иначе — `format(x, '.15g')`: у формулы не появляется `0.18700000000000003`. Целое — без дробной части;
- дата — ISO;
- `True` / `False` — `TRUE` / `FALSE`;
- перевод строки в ячейке — пробел;
- у формулы — сохранённое значение; его нет — ячейка пустая.

Битая или зашифрованная книга — текста нет.

### 9.2. docx

`word/document.xml` разбирается стандартными `zipfile` и `xml.etree.ElementTree`.

**Защита:**
- XML с `<!DOCTYPE` отвергается: ElementTree раскрывает внутренние сущности;
- размер распакованного файла проверяется потоковым чтением до предела, а не по `ZipInfo.file_size`.

**Тело читается по порядку:**
- абзацы: `w:t`; `w:tab` — табуляция; `w:br` — перевод строки;
- `w:ins` входит; `w:del`, `w:delText`, `w:instrText` — нет;
- таблицы: строка — ячейки через табуляцию, абзацы ячейки — через пробел; вложенные таблицы разворачиваются.

**Страницы.** Новая страница начинается на `w:br w:type="page"` и на `w:lastRenderedPageBreak` (так Word запоминает разбиение на страницы при сохранении). Разрыв на ещё пустой странице новой страницы не начинает: ручной разрыв и отметка Word рядом дают одну страницу, а не две. Документ без отметок — одна страница. Колонтитулы, сноски и примечания не входят.

### 9.3. Пределы и кэш

- **Пределы.** Распакованный `document.xml` больше 64 МиБ или текст больше 50 млн знаков, в xlsx — больше 5 млн обойдённых ячеек (пустые тоже), нехватка памяти при разборе — текста нет (`no_text`). Подрезанный текст дал бы ложное «цитата не найдена».
- **Без текста по-прежнему:** `.doc`, `.xls`, `.odt`, `.ods`, `.pptx`.
- **Кэш.** Миграция `0006` удаляет строки `object_text` страницы 0 у версий файлов с именами на `.docx`, `.xlsx`, `.xlsm` — следующее обращение извлечёт текст заново. Ключ кэша остаётся `digest`.

Итоги `no_text` в уже записанных строках `source` остаются до повторной сверки (разд. 12).

## 11. Ошибки и наблюдаемость

- **`check.CheckError(ValueError)`** — неверный вызов, до любой записи: пустая пачка (нет ни записей, ни связей), соединение без autocommit, задачи (`activity`) нет. Неизвестный `target` — данные агента, а не вызов: замечание `schema`. Ошибки данных — не исключения, а замечания отчёта.
- **`review.ReviewError(ValueError)`** — отказ в решении или захвате:
  - пункта нет, он закрыт или устарел;
  - аренда чужая;
  - нет прав на причину;
  - исход недопустим;
  - `confidence` вне 0–1 или не задана у модели.
- **Ошибки окружения** (`StoreError`, `psycopg.OperationalError`, `EmbeddingError` явного провайдера) уходят наверх, в базе ничего не меняется.
- **Каждое ослабление** видно в отчёте, а не скрыто: нет вектора (`degraded`), у источника нет текста (`no_text`), числа не с чем сверить (`numbers_unchecked`).

## 12. Вне подпроекта

- **Повторная сверка источников** (`recheck_sources`): после смены извлекателя, для итогов `error` и старых `no_text` у docx/xlsx. Она должна сначала проверять корень хранилища (`store.init(create=False)`): иначе неподключённый том даст лавину `no_file`. Подпроект 4, вместе с CLI.
- **Доля аудита по ошибкам** и **метрика калибровки** уровня 5 — после пилота.
- PRONOM и `format_puid`; `.doc`, `.xls`, `.odt`, `.pptx`; селектор `range` с проверкой ячеек.

## 14. Риски

| Риск | Что делаем |
|---|---|
| Сверка чисел ложно отклоняет верные атомы | Отчёт перечисляет ненайденные числа; числа условий — предупреждение; пересчитанное помечается `role: derived`; разбираемые форматы пополняются по примерам пилота |
| `lastRenderedPageBreak` устарел, номера страниц docx расходятся с Word | Цитата ищется по всем страницам, расхождение даёт `moved`, а не отказ |
| Пороги дублей и уверенности не откалиброваны | Константы модуля; пилот меняет их одной правкой |
| Очередь растёт быстрее, чем её разбирают | `stats` показывает возраст и объём; уровень 5 разгружает `semantic`; правило «предупреждение — к человеку» пересматривается по данным пилота |
| Пакеты ждут полного снимка | Разделяемая блокировка объектов в пакете — цена того, что новая версия не теряет пересмотр; снимок держит блокировку только на время копии хранилища |
