# amem — подпроект 2: движок поиска, выдачи и бэкапа

Редакция 1 (03.11.2026).

Продолжение спецификаций `2026-10-19-schema-v1-postgres-reatomize-design.md` (разд. 2, 6, 8) и `2026-10-25-amem-core-split-design.md` (разд. 1, 9). Учтены практики Graphiti и Graphify из разбора `2026-10-31-best-practices-graphiti-graphify.md`: именованные рецепты вместо одного непрозрачного поиска, уверенность цепочки по слабейшему звену, машиночитаемые ослабления выдачи и local-first без скрытых обращений наружу.

## Цель

Дать ядру amem воспроизводимый поиск по текущим знаниям и понятную выдачу для будущих MCP, CLI и веб-интерфейса:

- русский полнотекстовый поиск и отдельный поиск марок `codes`;
- локальные эмбеддинги в PostgreSQL + pgvector, `halfvec` и HNSW;
- слияние списков через RRF и четыре именованных рецепта;
- обход графа с происхождением и уверенностью каждого пути;
- очки полезности как слабый сигнал ранжирования, не влияющий на истинность;
- дамп базы и проверяемое восстановление, включая идентичность базы.

Результат подпроекта — библиотека `amem`, SQL-миграции и тесты на PostgreSQL 18 и 16. Сервера, полноценного пользовательского CLI и фонового сервиса здесь ещё нет.

## Решения

| Вопрос | Решение |
|---|---|
| Что ищем | Атомы и сущности, только действующую ревизию каждой записи; история доступна отдельному рецепту «что изменилось» |
| Полнотекст | PostgreSQL `tsvector`, конфигурация `russian`, взвешивание полей и GIN |
| Марки | Нормализованный `codes`: точное совпадение через GIN, префикс через отдельную проекцию с B-tree |
| Вектора | pgvector `halfvec`, cosine, HNSW; вектор принадлежит ревизии и конкретной модели |
| Модель по умолчанию | `sentence-transformers/paraphrase-multilingual-MiniLM-L12-v2`, 384 измерения, через `fastembed`; смена модели — только после замера на контрольных вопросах |
| Объединение | До 50 кандидатов из каждого доступного канала, RRF с `k = 60`, затем слабый множитель полезности |
| Рецепты | `exact_fact`, `similar`, `what_changed`, `around_entity`; русские названия — только подписи для интерфейсов |
| Уверенность пути | Минимум по явно заданным `link.confidence`; неизвестное остаётся `null`, а не превращается в 1.0 |
| Полезность | Неизменяемые отметки по уже показанным атомам; экспоненциальное затухание, период полураспада 180 дней |
| Бэкап | `pg_dump -Fc` + манифест с SHA-256; восстановление только в пустую базу; полный снимок включает OCFL-хранилище |
| Сеть | Нужна только при первой явно разрешённой загрузке модели; поиск и тесты сети не требуют |
| Совместимость | PostgreSQL 18 и 16, pgvector 0.8; без возможностей, доступных только в 18-й версии |

## 1. Границы и устройство

Новые модули:

- `amem/search.py` — общий вход, фильтры, каналы, RRF, компактная выдача;
- `amem/recipes.py` — четыре именованных рецепта и их параметры;
- `amem/embed.py` — интерфейс модели, локальный backend, индексация и переключение модели;
- `amem/usefulness.py` — выдача `retrieval`, отметки `atom_use`, счёт с затуханием;
- `amem/backup.py` — дамп, манифест, полный снимок, восстановление и ротация;
- `amem/sql/0005_search.sql` — расширение `vector`, поисковые проекции, эмбеддинги и журналы пользы.

`amem/lookup.py` остаётся источником полной записи, истории, источников и связей. Движок не дублирует правила выбора ревизии «на момент»: для текущей выдачи использует те же представления `atom_current` / `entity_current`, а полные записи собирает через `lookup`.

Поисковые таблицы — технические проекции, а не новые классы содержимого LinkML. Тело атома и сущности не меняется, версии `amem.atom/1` и `amem.entity/1` остаются прежними. Проверки `test_sql_schema.py` дополняются новыми служебными ограничениями; генерация Pydantic из-за этих таблиц не меняется.

Вне рамок:

- MCP/HTTP, полноценный CLI, хуки агентов и JSONL-журнал запросов — подпроект 4;
- очередь автопроверки и пересмотр по новой версии объекта — подпроект 3;
- веб-UI, отображение очков человеку и экспорт антологии — подпроект 5;
- переранжировщик, PPR/HippoRAG, GraphRAG, ColBERT и автоматическое расширение выдачи соседями — только после 30+ контрольных вопросов и отдельного замера;
- выбор bge-m3 или USER-bge-m3 как новой основной модели — отдельный эксперимент, не условие этого подпроекта.

## 2. Поисковая проекция

### 2.1. Таблицы

`search_document`:

- `target` (`atom` / `entity`), `record_id`, `revision_id`;
- `content_hash` — контроль того, какая ревизия проиндексирована;
- `document text` — нормализованный текст для эмбеддинга;
- `search_vector tsvector` — взвешённый полнотекстовый вектор;
- `codes text[]` — нормализованные марки;
- `updated_at timestamptz`;
- первичный ключ `(target, record_id)`, уникальный `(target, revision_id)`.

Индексы: GIN по `search_vector`, GIN по `codes`, внешний ключ от `revision_id` невозможен из-за общего полиморфного ключа, поэтому целостность обеспечивает запись через ядро и проверяют тесты. Удаление записей схемой запрещено; проекция может перестраиваться без потери знаний.

`search_code`:

- `target`, `record_id`, `code`;
- первичный ключ `(target, record_id, code)`;
- B-tree по `code` и по `code text_pattern_ops` для префиксного запроса.

Отдельная проекция нужна потому, что GIN по массиву даёт точное содержание элемента, но не эффективный префиксный поиск внутри элемента.

### 2.2. Текст и веса

Один детерминированный `search_text(payload)` собирает текст без имён JSON-полей, UUID, технических полей и источников:

- вес A — `label.ru` атома или сущности;
- вес B — простое объяснение, основное утверждение, термин или описание;
- вес C — остальное содержимое `content`, включая подписи и текстовые ячейки таблиц; у сущности — `description`;
- вес D — `aliases`, `codes` и `retrieval_context`.

Порядок фрагментов стабилен, строки приводятся к NFC, повторы в пределах одного поля убираются. Пустой текст допустим: запись остаётся доступной по id, ключу, коду и графу. Цитаты и содержимое файлов-источников в документ атома не копируются — иначе одинаковая цитата у многих атомов загрязняла бы выдачу.

`document` для эмбеддинга собирается из тех же смысловых полей без весов PostgreSQL. Изменение алгоритма текста требует версии `search_text_version` в манифесте проекции и полной переиндексации; вектор старого текста не считается актуальным.

### 2.3. Нормализация марок

Для `codes` используется единая функция на основе `sources.normalize`: NFC, нижний регистр, `ё → е`, единое тире, латинские двойники кириллицы → кириллица, схлопывание пробелов. Для марки пробелы вокруг дефиса и точки убираются, но буквы не склеиваются через дефис: `Вн-45`, `вн–45` и `ВН - 45` дают один код, а `РСК-14` не превращается в `рск14`.

Ввод запроса нормализуется тем же путём. Точное совпадение и префикс — разные машиночитаемые виды совпадения. Полнотекст не заменяет этот канал: PostgreSQL справедливо разбирает марки на части, а amem ищет обозначение целиком.

### 2.4. Обновление

Проекция обновляется в той же транзакции, что и пакет изменений:

- новая действующая ревизия заменяет строку `search_document`;
- более новая `pending`-ревизия не вытесняет подтверждённую текущую;
- `accepted` / `declined` обновляет проекцию вместе со сменой текущей ревизии;
- смена статуса не переписывает текст, но сразу меняет доступность записи фильтрам;
- отклонённый пакет не оставляет поисковой строки.

Повторная сборка `rebuild_search(conn)` идемпотентно перестраивает проекцию из текущих ревизий. Тест сравнивает её с построчной проекцией после записи: расхождение означает, что один из путей записи забыт.

## 3. Эмбеддинги

### 3.1. Хранение

`embedding_model`:

- `id`, `name`, `version`, `dims`, `backend`, `active`, `created_at`;
- уникальность `(name, version, backend)`;
- частичный уникальный индекс позволяет только одну `active = true` модель.

`embedding`:

- `target`, `revision_id`, `model_id`, `dims`, `text_hash`, `vec halfvec`, `created_at`;
- уникальность `(target, revision_id, model_id)`;
- `dims` повторяется в строке, чтобы частичные HNSW-индексы могли выбирать подходящую размерность без join.

В первой миграции создаются частичные HNSW-индексы для 384 и 1024 измерений (`halfvec_cosine_ops`). Новая размерность требует новой миграции; динамического SQL из пользовательского ввода нет. Проверка размерности выполняется до записи.

Вектор принадлежит ревизии, а не атому вообще. В поиске участвуют только вектора текущей ревизии активной модели с совпадающим `text_hash`. Старые вектора остаются после смены модели, пока отдельная операция очистки не удалит неактивную модель.

### 3.2. Backend и отсутствие скрытой сети

Общий интерфейс `EmbeddingProvider.embed(texts) -> vectors` позволяет тестам использовать детерминированную модель-заглушку. Реальный backend — `fastembed`, зависимость подключается extra `amem[embed]`; `pgvector` — обычная зависимость для адаптации векторов psycopg.

`AMEM_BACKEND=none` полностью отключает вычисление эмбеддингов. Поиск продолжает работать по кодам и полнотексту. Рецепт, запрошенный как семантический, возвращает `semantic: unavailable` и доступный текстовый результат либо пустой результат — без молчаливого утверждения, что векторный канал выполнялся.

Загрузка модели ленивая и явная: первый вызов локального backend может скачать модель только если это разрешено настройкой. Приложение с `none` и CI никогда не скачивают модель. Облачных провайдеров в этом подпроекте нет.

### 3.3. Индексация и смена модели

Запись ревизии не вызывает модель внутри транзакции PostgreSQL. Ядро предоставляет:

- `embed_revision(...)` — явно векторизовать одну ревизию;
- `sync_embeddings(...)` — пакетно заполнить отсутствующие вектора активной или указанной неактивной модели;
- `embedding_coverage(...)` — сколько текущих документов имеет актуальный вектор;
- `activate_model(...)` — переключить активную модель после полного покрытия текущих документов и внешней проверки качества.

Покрытие меньше 100 % — активация отклоняется с числом недостающих документов. Это исключает исчезновение части базы из семантического поиска без предупреждения. Повторный `sync_embeddings` не пересчитывает совпадающий `text_hash`.

## 4. Каналы, RRF и выдача

### 4.1. Общие параметры

`search` и текстовые рецепты принимают:

- `query`;
- `limit` (по умолчанию 10, максимум 100);
- `target`, `kind`, `entity_class`, `statuses` — необязательные фильтры;
- `include_record` — полная запись через `lookup.get`, по умолчанию выдача компактная;
- `usefulness` — включён по умолчанию, отключается для воспроизводимых замеров.

По умолчанию исключены `rejected`, `deprecated`, `superseded`. `draft` и `needs_review` остаются в выдаче со своим явным статусом. Фильтры применяются внутри каждого канала до отсечения топ-50: иначе первые 50 неподходящих записей вытесняли бы подходящие ещё до RRF.

### 4.2. Каналы

1. `code_exact` — нормализованный код совпал целиком.
2. `code_prefix` — код начинается с запроса; точные совпадения из этого списка исключаются, чтобы не получать двойной вес.
3. `fts` — `websearch_to_tsquery('russian', query)`, ранг `ts_rank_cd` по взвешённому вектору.
4. `vector` — косинусное расстояние по активной модели, только актуальные вектора.

Для векторного канала с фильтрами включается `hnsw.iterative_scan`. Каждый канал отдаёт не более 50 записей. Пустой или неприменимый канал не считается ошибкой; использованные и пропущенные каналы видны в метаданных ответа.

### 4.3. Слияние

Для записи со строками рангов `r_i`:

```
rrf = Σ weight_i / (60 + r_i)
usefulness_multiplier = min(1.25, 1 + beta * ln(1 + useful_score))
final_score = rrf * usefulness_multiplier
```

Начальные параметры: `k = 60`, `beta = 0.05`, потолок множителя `1.25`. Они версионируются в ответе как `ranking_version`, а окончательная калибровка выполняется на контрольных вопросах. Веса каналов принадлежат рецепту, не свободному пользовательскому SQL.

Порядок стабилен: `final_score` по убыванию, затем каноническая ссылка `atm:/ent:<UUID>` по возрастанию. Время запроса не меняет порядок, если зафиксированы база и момент расчёта полезности.

**Исключение для точного факта:** в `exact_fact` все `code_exact` идут раньше любых неточных совпадений. Полезность упорядочивает точные совпадения только внутри их группы и не позволяет популярному атому обойти точную марку.

### 4.4. Компактный результат

Ответ содержит:

- `recipe`, `ranking_version`, `channels`, `semantic` (`used` / `unavailable` / `not_requested`);
- `items`: `ref`, `revision`, `label`, `snippet`, `status`, `review_state`, `score`, `matches`;
- каждый элемент `matches`: канал, место в канале и исходный ранг/расстояние, если оно есть;
- `retrieval_id` — для последующей отметки полезности;
- при `include_record=true` — поле `record` в существующем формате `lookup.get`.

Очки полезности и их множитель в обычную карточку не входят. Это не оценка достоверности и не должно подталкивать агента выбирать популярное. `snippet` — короткий фрагмент найденного текста, а не новый ответ модели; никакого LLM в выдаче нет.

## 5. Именованные рецепты

### 5.1. `exact_fact` — «точный факт»

Для марки, обозначения или конкретной формулировки.

- каналы: `code_exact` с наивысшим приоритетом, `code_prefix`, `fts`, затем `vector` как слабое дополнение;
- точный код всегда предшествует остальным;
- если запрос совпал с несколькими записями, возвращаются все кандидаты до `limit` — ядро не угадывает одну запись;
- пустая выдача — пустой список, а не ближайший по смыслу ответ без пометки.

### 5.2. `similar` — «похожее»

Для поиска дублей и близких по смыслу атомов.

- вход: текст либо существующий `atm:` / `ent:`;
- для записи используется вектор её текущей ревизии, сама запись исключается из результата;
- основной канал — `vector`, дополнительный — `fts`;
- при недоступной модели честно работает только `fts` и отмечает `semantic: unavailable`;
- сходство не меняет статус и не создаёт `same_as`: решение о дубле остаётся за проверкой.

### 5.3. `what_changed` — «что изменилось»

Для аудита записи или набора записей за интервал.

- вход: необязательные `ref`, `since`, `until`; границы — время с часовым поясом, `since < until`;
- события: новые ревизии, решения проверки, смены статуса, появление и вывод связей из оборота;
- у ревизии возвращаются номер, `recorded_at`, старый/новый `content_hash` и детерминированный список изменённых JSON-путей; массив сравнивается как одно значение;
- отдельно сохраняются `valid_from` / `valid_to`: время действия не подменяет время записи;
- порядок: время, затем тип события и id; отменённые события истории не стираются.

Это не текстовый поиск: рецепт читает журналы и ревизии напрямую. Он не создаёт `retrieval` для отметок полезности.

### 5.4. `around_entity` — «вокруг сущности»

Для ответа «что связано с этой записью и насколько надёжен путь».

- вход: `atm:` или `ent:`, `depth` от 1 до 3 (по умолчанию 1), необязательные виды связей и статусы;
- обходятся действующие `link` в обе стороны, а для текущих ревизий атомов также `atom_about` и `atom_derived`;
- BFS возвращает кратчайшие пути, циклы обрезаются по посещённым записям; один и тот же узел не раздувает выдачу;
- результат включает узлы, рёбра, направление, происхождение связи и весь путь от исходной записи;
- никакого автоматического PPR или скрытого добавления соседей к текстовому поиску.

Для каждого пути:

- `confidence = min` явных `link.confidence` на пути;
- если хотя бы у одной пройденной `link` уверенность `NULL`, итоговая уверенность `NULL`;
- структурные поля `about` / `derived_from` не получают выдуманное число; их тип виден в ребре;
- если на пути вообще нет явно оценённых связей, `confidence = NULL`, а не 1.0;
- отдельный `evidence_role` — самая слабая роль источников атомов пути в порядке `primary` → `secondary` → `derived`; без источников — `NULL`.

Таким образом число и качество доказательств не смешиваются, а слабое звено нельзя скрыть усреднением.

## 6. Очки полезности

### 6.1. Журнал выдачи и отметок

`retrieval`:

- `id`, `activity` (необязательно), `recipe`, `query`, `agent`, `created_at`, `ranking_version`.

`retrieval_item`:

- `retrieval_id`, `atom_id`, `rank`;
- уникальность `(retrieval_id, atom_id)` и `(retrieval_id, rank)`;
- сохраняются только атомы: отмечать сущности как полезные в этой версии нельзя.

`atom_use`:

- `id`, `atom_id`, `retrieval_id`, `activity`, `agent`, `used_at`;
- неизменяемая строка, как запись `status_log`;
- уникальность `(activity, atom_id)` — одна отметка атома за задачу, даже если он встречался в нескольких выдачах.

`mark_helpful` принимает `retrieval_id`, `activity` и список атомов. Проверяется, что каждый атом действительно был в этой выдаче и что выдача относится к той же задаче. Повторная идентичная отметка идемпотентна; попытка отметить непоказанный атом — машиночитаемая ошибка с id отклонённых записей, без частичной записи пачки.

Полные ответы и тела записей в `retrieval` не копируются. JSONL-журнал длительности и числа находок появится вместе с сервером в подпроекте 4.

### 6.2. Счёт

Для отметки `i`:

```
weight_i = 0.5 ** (age_days_i / 180)
useful_score = Σ weight_i
```

Возраст отрицательным быть не может; время расчёта передаётся явно в тестах. Отметки принадлежат атому, а не ревизии и переживают правки. Новый атом имеет счёт 0 и множитель 1 — нейтральный старт, не штраф.

Полезность влияет только на порядок. Она не участвует в `status`, `review_state`, `confidence` и `evidence_role`. При будущем `kb_merge` все журнальные отметки дубля должны быть перенесены к оставшемуся атому в той же транзакции; сам `kb_merge` в этот подпроект не входит.

## 7. Бэкап и восстановление

### 7.1. Дамп PostgreSQL

`backup.create(...)` запускает `pg_dump -Fc` напрямую, без shell, с параметрами отдельным списком. Пароль не попадает в командную строку, манифест или журнал. Файл сначала пишется во временное имя и после успешного завершения атомарно переименовывается:

`data/backups/pg/ГГГГ-ММ-ДДTЧЧ-ММ-ССZ.dump`.

Рядом создаётся JSON-манифест с версией формата, именем файла, размером, SHA-256, временем, версией сервера и `pg_dump`, `base_id` из `meta`, версиями миграций и `search_text_version`. Существующий файл не перезаписывается. По умолчанию хранятся последние 14 успешных дампов; неполные файлы и манифесты без дампа не считаются копиями.

### 7.2. Полный снимок

Полный бэкап — не один `.dump`, а:

- дамп PostgreSQL и его манифест;
- копия `data/objects` со всеми OCFL-инвентарями и версиями файлов;
- корневой манифест, связывающий обе части по `base_id` и SHA-256.

Копирование OCFL выполняется во временный каталог с последующим атомарным переименованием. Пути из манифеста при восстановлении не могут выходить за целевой корень. Настройки, пароли, `.env`, кэш моделей и журналы запросов в бэкап не входят.

### 7.3. Восстановление

`backup.restore(...)`:

- принимает только пустую целевую базу и пустой/несуществующий каталог объектов;
- проверяет SHA-256 до запуска `pg_restore`;
- не использует `--clean` против существующих данных и не перезаписывает рабочую базу;
- после восстановления сверяет `base_id`, применённые миграции, число основных записей и целостность OCFL;
- отдельный `backup.verify(...)` выполняет пробное восстановление во временную базу, а не только проверку хэша.

Дамп включает поисковые проекции и вектора, но после восстановления `rebuild_search` и `sync_embeddings` остаются безопасными способами починить производные данные. Тест восстановления проверяет не только числа строк, но и фактический поиск.

## 8. Ошибки и наблюдаемость

Все публичные функции возвращают структурированные данные либо вызывают типизированные ошибки ядра с понятным полем:

- неверный `ref`, интервал, `depth`, `limit`, размерность вектора;
- модель не установлена или backend отключён;
- активация при неполном покрытии;
- атом не принадлежит выдаче или задаче;
- повреждённый/неполный бэкап и непустая цель восстановления.

Нет автоматических повторов скачивания, скрытого выбора облака и «успешного» векторного поиска без векторов. Для поиска возвращаются длительность каналов, число кандидатов и покрытие активной модели; для бэкапа — путь, размер и итог проверки. Это библиотечные значения, а не фоновые метрики сервера.

## 9. Приёмка

Вся существующая серия остаётся зелёной. Новые тесты идут на PostgreSQL 18 и 16 через существующую фикстуру `pg`; отсутствие базы — ошибка, не skip. Модель-заглушка даёт фиксированные вектора, внешняя модель в CI не скачивается.

### 9.1. Полнотекст и коды

- `Вн-45`, `РСК-14`, `F50.0214` находятся по `codes` в разном регистре, с разными тире и латинскими двойниками;
- префикс возвращает кандидатов, но не равен точному совпадению;
- «ветрового давления» находит атом с «ветровое давление»;
- вес A/B/C/D и пустой документ не приводят к SQL-ошибкам;
- `rejected`, `deprecated`, `superseded` исключены по умолчанию; явный фильтр статуса работает;
- новая `pending`-ревизия не подменяет текст текущей; `accepted` / `declined` обновляет его;
- полная перестройка проекции совпадает с проекцией, полученной при записи.

### 9.2. Вектора и RRF

- `halfvec` + HNSW работает на 384 измерениях на обеих версиях PostgreSQL; 1024 проверяется регистрацией модели и индексом;
- неверная размерность и вектор другой модели не попадают в выдачу;
- смена активной модели невозможна при неполном покрытии, возможна после `sync_embeddings`, старые вектора сохраняются;
- `AMEM_BACKEND=none` не вызывает provider и явно сообщает `semantic: unavailable`;
- RRF воспроизводится на заранее посчитанном примере, учитывает веса рецепта и стабильно разрешает равенство;
- фильтры применяются до топ-50, а `limit` и детерминированный tie-break соблюдаются.

### 9.3. Рецепты и уверенность

- `exact_fact`: точная марка опережает более популярный текстовый результат; неоднозначность возвращает кандидатов;
- `similar`: исходная запись исключена, семантический и ослабленный текстовый режимы различимы;
- `what_changed`: видны ревизии, статусы, решения проверки и связи за интервал; время действия не подменяет `recorded_at`;
- `around_entity`: учитываются `link`, `about`, `derived_from`, направление и циклы; глубина ограничена;
- путь с уверенностями `0.9` и `0.4` получает `0.4`; `NULL` остаётся `NULL`; слабая роль источника становится `evidence_role` пути;
- очки не меняют ни уверенность, ни статус, ни итог проверки.

### 9.4. Полезность

- отметить можно только атом из указанной выдачи и той же задачи;
- повтор за задачу идемпотентен, чужой атом отклоняет всю пачку;
- правка атома сохраняет счёт;
- счёт с двумя отметками разного возраста совпадает с формулой полураспада при фиксированном `now`;
- новый атом имеет множитель 1; популярность не обходит точный код и не превышает потолок;
- `retrieval_item` не позволяет отметить сущность или непоказанный атом.

### 9.5. Бэкап

- дамп и манифест создаются атомарно, SHA-256 сходится, повтор не перезаписывает копию;
- ротация оставляет 14 полных копий и не принимает `.tmp` за готовый бэкап;
- восстановление на PostgreSQL 18 и 16 возвращает тот же `base_id`, миграции, ревизии, связи, источники, отметки и поисковую выдачу;
- полный снимок восстанавливает OCFL-объект, и старая ссылка источника открывает прежнюю версию;
- повреждённый файл, несовпадающий манифест, непустая база/папка и выход пути за целевой корень отклоняются;
- `backup.verify` выполняет настоящее пробное восстановление и фактический поиск.

**Подпроект готов**, когда эти проверки и все прежние тесты проходят на PostgreSQL 18 и 16, `tools/gen_schema.py --check` чист, а CI публичного репозитория зелёный.

## 10. Риски

| Риск | Что делаем |
|---|---|
| Популярность подменяет релевантность | Слабый ограниченный множитель, нейтральный старт, отдельная группа точных кодов, контрольные вопросы |
| Неизвестная уверенность выглядит как полная | `NULL` сохраняется; числовая уверенность и роль доказательств разделены |
| Смена модели скрыто ухудшает покрытие | Активация только при 100 % актуальных векторов текущих документов; старые вектора сохраняются |
| Поисковая проекция расходится с ревизиями | Обновление в транзакции записи + идемпотентная перестройка + тест эквивалентности |
| Модель делает ядро тяжёлым или сетевым | extra `embed`, `AMEM_BACKEND=none`, заглушка в тестах, FTS продолжает работать |
| HNSW при фильтрах возвращает мало кандидатов | `hnsw.iterative_scan`, фильтры внутри каналов, замеры на контрольных вопросах |
| Дамп есть, но восстановление не проверено | Обязательный restore-тест и фактический поиск после восстановления на обеих версиях |
| Полный снимок расходится с объектами | Единый манифест с `base_id`, атомарная сборка, проверка OCFL и версии источника |
| Движок преждевременно обрастает сервером и графическими алгоритмами | Только библиотека и четыре рецепта; PPR, reranker, MCP/CLI и UI остаются в своих подпроектах |
