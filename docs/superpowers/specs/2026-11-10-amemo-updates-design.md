# amemo — обновления: версия, релизы GitHub, автообновление

**Задача (пользователь, 10.11).** Приложение показывает текущую версию, следит за релизами на GitHub и обновляется само. Автообновление включено по умолчанию, его можно выключить.

## 1. Что есть сейчас

- **Версия.** `amemo.__version__` и `amemo_web.__version__` — одна и та же (`tools/release.py versions` сверяет). Сейчас `0.1.0a1`. Служба отдаёт её в `GET /api/v1/session` (`amemo_version`); веб показывает в «Настройках».
- **Релиз.** Метка `v*` на `main` запускает workflow `release`: сборка веба, sdist и колёса, проверка в чистом окружении, загрузка на PyPI. Релиза на GitHub (GitHub Release) workflow **не создаёт** — следить пока не за чем.
- **Установка** бывает трёх видов:
  - `pipx install "amemo[web]"` — основной путь из README;
  - образ Docker (`Dockerfile`, `docker-compose.yml`);
  - исходники для разработки (`pip install -e`).

## 2. Решения

1. **Источник правды о релизах — GitHub Releases** (`GET https://api.github.com/repos/empty-complete/amemo/releases`), как просил пользователь. Пакет ставится с PyPI той же версии: релиз GitHub создаёт workflow `release` после успешной загрузки на PyPI, поэтому версия из релиза на PyPI уже есть.
2. **Канал и выбор релиза.**
   - Канал — по текущей версии:
     - стоит предварительная (`a`, `b`, `rc`) — канал `pre`: видит и стабильные, и предварительные релизы, берётся наибольшая;
     - стоит стабильная — канал `stable`, только стабильные.
   - Черновики пропускаются, и релизы без колеса на PyPI тоже.
   - Порядок — по `packaging.version.Version`, а не по дате.
3. **Проверка** — при старте и раз в 6 часов, с `If-None-Match` (ETag). Это укладывается в лимит API без токена: 60 запросов в час с адреса. Без сети или при ошибке API — тихо, следующая попытка по расписанию; в «Настройках» — время и итог последней проверки.
4. **Автообновление — по умолчанию включено.**
   - Выключается настройкой `auto_update = false` (`amemo.toml` или `AMEMO_AUTO_UPDATE`) или переключателем в «Настройках». Переключатель пишет в файл состояния службы `AMEMO_STATE/updates.json`, а не в `amemo.toml`: конфиг пользователя служба не переписывает.
   - Если выключено, служба только сообщает «доступна версия X» и даёт кнопку «Обновить сейчас».
5. **Как ставится** — зависит от вида установки, определяется при старте:

   | Установка | Признак | Обновление |
   |---|---|---|
   | pipx | `sys.prefix` внутри venvs pipx и поставлен через `pipx install` (не временный venv `pipx run`) | `pipx install --force "amemo[web]==X"` (именно X, не «последняя») |
   | pip в venv | venv пишется текущим пользователем, пакет не editable | `sys.executable -m pip install "amemo[web]==X"` без `--index-url`: зеркало и настройки pip пользователя работают |
   | Docker | `/.dockerenv` или `AMEMO_IN_CONTAINER` | не ставит; «Доступна X — обновите образ» и команда |
   | исходники (editable) | `direct_url.json` с `editable` | не ставит; только сообщает |

   - После установки сверить `importlib.metadata.version("amemo") == X` и `amemo_web` той же версии. Не сошлось — `failed`.
   - Установка и `updates.json` — под файловой блокировкой (`fcntl`): `amemo update` из CLI и служба не ставят одновременно.

6. **Проверка до замены, бэкап, перезапуск в простое.**
   1. **Временное окружение.** Новая версия ставится во временный venv: `python -m venv` в `AMEMO_STATE/updates/X`, затем `pip install "amemo[web]==X"`.
   2. **Проверка там же:** `python -m amemo.service --check`. Без записи в базу:
      - сборка приложения и `/ui`;
      - новые миграции применяются в транзакции с `ROLLBACK` на рабочей базе, под тем же advisory-замком, что `db.migrate`.

      Не прошла — `failed`, «обновление до X не встало: …», эта версия больше не пробуется. Рабочая установка не тронута.
   3. **Бэкап — обязателен перед новыми миграциями.** `backup.create`, если у новой версии они есть. Бэкап невозможен (нет клиента PostgreSQL 18 или `AMEMO_PG_BIN`, нет места) — версия не ставится: `available`, «нужен бэкап: …». Ручное «Обновить сейчас» тоже идёт только после бэкапа.
   4. **Установка на место** — только после успешной проверки: pipx или pip, как в п. 5. Упала — запасной откат: переставить прежнюю `==`, если она доступна. Временный venv удаляется.
   5. **Перезапуск в простое:**
      - нет HTTP-запросов 2 минуты;
      - нет открытой транзакции записи;
      - не идёт загрузка или выгрузка подборки;
      - нет задачи в состоянии `installing`.

      Открытые сессии MCP по HTTP и SSE простою не мешают: они висят всегда. Перезапуск — `os.execv` того же процесса с теми же аргументами; при старте `db.prepare` применяет миграции.
   6. **В вебе:** при возврате связи веб видит новую версию в `/session` и предлагает перезагрузить страницу.
   7. **Долгие процессы `amemo mcp` (stdio) у агентов.** После установки они работают со старым кодом в памяти и новыми файлами на диске.
      - `amemo mcp` при старте импортирует всё нужное заранее и раз в несколько минут сверяет версию на диске (`importlib.metadata`).
      - Версия сменилась — инструменты отвечают «amemo обновлён — перезапустите агента», процесс завершается после текущего вызова.
      - Хуки — новый процесс на каждый вызов, их это не касается.
7. **Права — и в локальной, и в общей службе (`AMEMO_TOKENS`).**
   - Смотреть статус и запускать проверку (`GET /updates`, `POST /updates/check`) может любой с правом чтения: это безвредно.
   - Включать, выключать (`PUT`) и ставить (`POST /updates/install`) — только человек (`person:`) с правом записи.
   - У модели инструмента обновления в MCP нет.
8. **Безопасность.**
   - Ставится только точная версия с PyPI из релиза нашего репозитория. Адрес репозитория зашит в код, из настроек его не взять.
   - Без токенов и без запуска чужих скриптов: только `pipx` и `pip` той же среды.
   - В журнале службы: что, когда и каким способом ставилось.

## 3. Контракт

- `GET /api/v1/updates` → `UpdateStatus`:
  - `current` — текущая версия;
  - `latest` — версия и адрес релиза или `null`;
  - `channel` — `stable` или `pre`;
  - `install` — `pipx`, `pip`, `docker` или `source`;
  - `auto` — `true` или `false`;
  - `state` — `idle`, `checking`, `available`, `installing`, `ready`, `restarting` или `failed`;
  - `checked_at`;
  - `message` — словами: что произошло, что делать.
- `PUT /api/v1/updates` `{auto}` — только человек с правом записи.
- `POST /api/v1/updates/check` — проверить сейчас; может любой с правом чтения.
- `POST /api/v1/updates/install` — поставить доступную сейчас; только человек с правом записи.
  - При `docker` и `source` — 409 `update_unsupported` с командой словами.
  - Без возможного бэкапа при новых миграциях — 409 `backup_required` с причиной.

## 4. Веб

- **Настройки → «Версия и обновления».**
  - Текущая версия.
  - Итог последней проверки («Последняя проверка: 10 минут назад, обновлений нет»).
  - «Доступна 0.1.0a2» — ссылка на релиз, кнопка «Обновить сейчас».
  - Переключатель «Обновляться автоматически», по умолчанию включён.
- **Верхняя строка** — значок только в двух случаях:
  - «Обновление установлено — перезапуск, когда служба освободится»;
  - «Обновление не встало».

  В остальное время — ничего: тихо.
- **После перезапуска** — плашка «amemo обновлён до X — перезагрузите страницу», если версия в `/session` отличается от той, с которой открыта страница.

## 5. Части и порядок

| Часть | Что | Кто |
|---|---|---|
| U1 | Workflow `release` создаёт GitHub Release (заметки из коммитов с прошлой метки) после загрузки на PyPI | сессия релизов |
| U2 | `amemo/updates.py`: выбор релиза, вид установки, временный venv и `--check`, обязательный бэкап, установка на место, перезапуск в простое, блокировка, состояние в `AMEMO_STATE/updates.json`; `amemo update` в CLI; сверка версии в `amemo mcp`; пути `/updates` в контракте и службе; тесты с подставным API GitHub и подставным `pip` | служба (сессия службы, 10.11) |
| U3 | Веб: «Версия и обновления» в настройках, значок в верхней строке, плашка после перезапуска; моки по контракту; e2e на моках | веб |

Проверки — в CI. Ничего не ставить и не перезапускать на машине разработчика при тестах: установщик и перезапуск подставляются.

## 6. Риски

| Риск | Что делаем |
|---|---|
| Новая версия не запускается | Проверка во временном venv до замены, рабочая установка не тронута; запасной откат на прежнюю `==` — только если она доступна (её может не быть на PyPI: локальное колесо, разработка) |
| Новая версия стартовала, применила миграции и упала | Откатить базу нельзя — честно: «восстановите из бэкапа <путь>» и команда `amemo backup restore <путь>` в журнале и в `message`. Поэтому без бэкапа версия с новыми миграциями не ставится вовсе |
| Миграция портит базу | Миграции новой версии заранее проверяются в транзакции с откатом; бэкап перед заменой обязателен |
| Долгие процессы `amemo mcp` после замены файлов | Импорт всего нужного при старте, сверка версии на диске, «перезапустите агента» и выход после текущего вызова |
| Служба и CLI ставят одновременно | Файловая блокировка установки и `updates.json` |
| Обновление посреди работы | Перезапуск только в простое; запись с окном отмены досылается до перезапуска (`keepalive`) |
| Лимит API GitHub | Раз в 6 часов, ETag, без токена |
| Docker и исходники | Не ставим, только сообщаем — образ и рабочую копию человек обновляет сам |
